# 실험: Memory Agent 백본 강화 (Qwen3-4B → GPT-5-Nano) — mem0-classic-oss

> 작성 2026-07-24. 배경: [custom-prompt-experiment.md](custom-prompt-experiment.md) · [mem0-halumem-baseline.md](mem0-halumem-baseline.md)
> **변인은 memory agent 백본 하나** (mem0의 추출·update 결정 LLM). 프롬프트는 default/custom 양쪽을 돌려 **백본×프롬프트 2×2**를 완성한다. Generator(답변 생성)는 Qwen3-4B 고정, judge는 gpt-5-nano(4유저) 고정.

## 1. 목적

- 병목 분석 결과 추출 커버리지(custom 프롬프트로 해소됨)와 update 디테일 보존·재작성 drift는 **백본 능력 문제**로 지목돼 왔음 — 백본을 강화하면 어떤 지표가 얼마나 움직이는지 실측
- 특히: ① update 결정 품질 (Upd C, decision_miss), ② 재작성 drift (유래별 Acc), ③ 지침 준수 (custom 프롬프트에서 문단형·"user 발화만" 준수 — Qwen은 과잉 준수+FMR 오염이 있었음)

## 2. 설계 결정

- **4유저 레인이 canonical.** 20유저 Stage A는 백본이 유료가 되면서 근거 상실 (4B judge 20u 행은 왜곡 있는 judge의 보조 비교였고, 신뢰 축은 nano judge 4u). 4유저 = QA 705·골든 1,861개로 방향 탐색엔 충분하며, 우승 조합 확정 시 그 조합만 20유저로 승격
- **코드 변경 불필요 (검증 완료)**: mem0 0.1.118 `LLMBase._get_supported_params`가 모델명 "gpt-5" 감지 시 temperature/max_tokens/top_p를 자동 필터링. `MEM0_LLM_MODEL` env 교체만으로 동작
- **reasoning effort는 기본값** (mem0 config로 전달 불가) — judge에서 쓰는 minimal이 아님. "백본 강화" 취지에는 부합하나 출력 과금이 늘어나는 요인으로 기록
- 임베더(서버 Qwen3-Embedding-4B)·Qdrant·top-k 20·데이터셋 첫 4유저 모두 기존과 동일

## 3. 비용 (trace 실측 외삽)

Stage A 20유저 기준 입력 ~11M tok + 출력 ~5M tok → 4유저는 ~20% → **런당 ~$0.6, reasoning 여유 포함 ~$1**. B-2 judge ~$1.1/런. 2런 총 **~$4 내외**.

## 4. 실행 (전부 서버, tmux)

```bash
# Run C: nano 백본 × default 프롬프트
OPENAI_BASE_URL=https://api.openai.com/v1 \
MEM0_LLM_MODEL=gpt-5-nano-2025-08-07 \
uv run python eval/mem0-classic-oss/eval_memzero_oss.py \
    --version nano4 --user-num 4 --top-k 20 --max-workers 20 --trace

# Run D: nano 백본 × custom 프롬프트 (토글 추가)
OPENAI_BASE_URL=https://api.openai.com/v1 \
MEM0_LLM_MODEL=gpt-5-nano-2025-08-07 MEM0_CUSTOM_FACT_PROMPT=halumem \
uv run python eval/mem0-classic-oss/eval_memzero_oss.py \
    --version nano4-custom --user-num 4 --top-k 20 --max-workers 20 --trace

# 이후 각 런에 대해 (버전명만 교체):
# A' — generator는 Qwen이므로 env 프리픽스 없이!
uv run python eval/mem0-classic-oss/gen_answers.py \
    --results results/mem0-classic-oss/memzero-oss-nano4/memzero-oss_eval_results.jsonl --max-workers 20
# B-2 — nano judge 4유저
OPENAI_BASE_URL=https://api.openai.com/v1 \
JUDGE_MODEL=gpt-5-nano-2025-08-07 JUDGE_REASONING_EFFORT=minimal \
uv run python eval/mem0-classic-oss/judge.py \
    --results results/mem0-classic-oss/memzero-oss-nano4/memzero-oss_eval_results.jsonl \
    --user-num 4 --max-workers 20 --out-dir results/mem0-classic-oss/judge-gpt5nano-4u-nano
# (Run D는 nano4 -> nano4-custom, out-dir -> judge-gpt5nano-4u-nano-custom)

# 로컬 동기화 후: 유래별 분해 + evidence 저장 교차검증
uv run python src/mem0-classic-oss/analyze_acc_by_origin.py \
    --artifacts results/mem0-classic-oss/memzero-oss-nano4/tmp \
    --judge results/mem0-classic-oss/judge-gpt5nano-4u-nano/judge
uv run python src/mem0-classic-oss/analyze_qa_evidence_storage.py \
    --judge results/mem0-classic-oss/judge-gpt5nano-4u-nano/judge
```

두 런 동시 실행 안전 (공유 상태 없음 — 버전별 컬렉션/디렉토리 분리, OpenAI rate limit만 공유).

## 7. 분석 — 셀마다 병목이 다르다

**① QA 최강 셀은 nano×default (49.79)** — Qwen×default 대비 +7.0pt, QA H는 29.08→22.84로 급감. **그런데 R은 오히려 최저(22.62)**: nano는 적게(3,544개), 짧고(76~80자) 깨끗하게 저장하고 재작성을 거의 안 하는데, 그 "적지만 깨끗한 저장소"가 검색·활용 단계에서 더 잘 먹힘. R(완전 포함 2점 비율)이 낮아도 WR 45.8로 부분 커버리지는 유지된다는 점과 합치면, **QA엔 커버리지 총량보다 저장소 청결도가 더 효과적**이라는 게 이 실험의 핵심 발견.

**② drift는 Qwen 특이 행동으로 확정.** UPDATE 비중 65.5%(Qwen) → 17.0%(nano), UPDATE-유래 Acc 20.4% → 40.3% (ADD-유래와 사실상 동급). 재작성을 덜 하고, 해도 덜 망가뜨림 → Acc 30.12→42.37 (+12.3pt). "0점의 80%가 재작성본" 문제는 백본 교체만으로 대부분 해소.
> **⚠ §14 정정**: 이 "재작성 drift" 귀속은 틀렸다. Qwen의 UPDATE는 97%가 **내용 무변경(no-op)** 이며, UPDATE-유래 Acc가 낮은 것은 재작성이 망가져서가 아니라 **갱신되지 않은 구버전이 후속 세션에 재등록돼** 그 세션 기준으로 채점되기 때문이다. "UPDATE 비중 65.5%"도 no-op 재등록을 센 값이다.

**③ FMR로 지침 준수의 백본 의존성 입증.** Qwen×custom에서 39.38로 추락했던 FMR이 nano×custom에선 60.82 — **default 수준(60.23)과 동일**. nano는 "user 발화만" 지침을 실제로 지켜서 distractor를 흡수하지 않음 (빈 세션 5~6/유저 증가도 같은 신호). Qwen custom의 R 61.47은 상당 부분 "지침 무시하고 세션 전체를 쓸어담은" 대가로 얻은 오염된 커버리지였던 것.

**④ custom 프롬프트는 nano에선 손해.** R 22.62→34.82로 오르긴 하나 Qwen custom(61.47)에 한참 못 미치고, Acc·QA 모두 default보다 나쁨 (QA C 39.29 = 최저 셀). 절제된 ~580자 문단 + 엄격한 필터링 → 후보 1,164개로 커버리지 부족. **프롬프트 효과는 백본 종속적** — Qwen에겐 커버리지 폭증(오염 동반), nano에겐 과잉 절제. 동일 개입이 백본에 따라 정반대 방향으로 작용하므로, 프롬프트 튜닝은 백본 확정 후에 해야 함.

**⑤ 병목 지도 (evidence 저장 교차검증)**: nano 두 셀 모두 실패 QA의 절반 이상이 "일부 미저장"(49.7%/60.6%)이고 "저장됐는데 못 씀"은 7.7%/9.6%뿐 — **nano 런의 병목은 다시 추출 커버리지로 회귀** (Qwen×custom의 37%와 대조적). 셀별 병목: Qwen×default = 추출+drift / Qwen×custom = 초장문 활용(생성) / nano×default·custom = 추출 커버리지.

**개선 방향 시사**: 현 최선 조합은 **nano 백본 × default 프롬프트** (QA C 49.79, Acc 42.37, H 최저). 다음 개입은 이 셀의 남은 병목인 커버리지 — "깨끗함을 유지한 채 더 많이 뽑기" (예: default 프롬프트에 커버리지 지시만 추가, 세션당 fact 수 하한, 2-pass 추출). Qwen 계열로 돌아갈 경우엔 재작성 억제가 선결 과제.

### 8-1. Run E (gpt-5-mini) 판독 — 2026-07-26

- **능력 사다리 유효, 포화 아님**: default 레인에서 4B→nano→mini 단조 개선 — QA C 42.84→49.79→**52.91**, Acc 30.12→42.37→**48.56**, Upd C 8.57→17.14→**27.56** (논문 GPT-4o mem0의 25.50을 넘어섬), UPDATE-유래 Acc 20.4→40.3→42.8%
- **"청결도" 재정의**: mini는 재작성 비중이 49.5%로 낮지 않은데(nano 17%) UPDATE-유래 Acc가 42.8%로 건강 — 관건은 **재작성 빈도가 아니라 재작성 품질**. Qwen의 문제는 "많이 고침"이 아니라 "고칠 때 망가뜨림"이었던 것
- **FMR 백본×프롬프트 상호작용 3형태**: custom 프롬프트가 FMR에 미치는 효과 — Qwen 급락(63→39), nano 불변(60→61), mini **개선**(52.83→64.33). 동일 개입의 부호가 백본마다 다름. 한편 default 레인에서 FMR은 능력이 올라도 하락 추세(63→60→53) — mini가 default에서도 171~223자로 길게 쓰며 distractor를 일부 흡수하는 트레이드오프
- **mini×custom의 극단 전략**: 세션의 15~35%를 통째로 빈 세션 처리 + 평균 1,461~2,393자 초대형 요약. 그런데도 R 42.67(자기 default보다 +6.8), Acc 55.07·Target P 94.14는 **전 셀 최고** — "선별한 세션만 정밀하게"가 정확도엔 최적이나 QA(46.52)는 default에 밀림 (빈 세션의 커버리지 손실이 QA에서 청구됨, evidence 미저장 51.6%)
- 실패 QA 분포(교차검증): mini-d 미저장 40.1%/완전저장 17.8% — 추출과 활용이 반반인 중간 체제. 병목이 단일 지점에서 분산 구조로 이행
- 현 순위 (QA C 기준): **mini-d 52.91** > nano-d 49.79 > Qwen-d 42.84 > … > nano-c 39.29

### 8-2. Run F (Qwen3-30B-A3B-Instruct) 판독 — 2026-07-26: "능력 vs family" 판정

- **재작성 품질은 family 각인으로 확정**: UPDATE-유래 Acc — Qwen 계열 20.4%(4B-d)/16.8%(4B-c)/**21.4%(30B-d)**/16.5%(30B-c) vs GPT 계열 40.3~52.9%. 파라미터 7.5배에도 품질 불변 → drift는 능력 부족이 아니라 **Qwen 스타일(및 mem0 update 프롬프트와의 궁합) 문제**. 반면 **재작성 빈도는 능력 따라 완화** (65.5%→41.7%) — 빈도와 품질이 서로 다른 축에 지배됨

5. **custom 전패 패턴, 6번째 백본에서도 유지** (QA 55.49 < 58.54). 문단형(평균 387자, 빈세션 13~20) ADD의 87.4%가 1점(부분 근거) — 문단 묶음이 세션 경계를 넘나들며 부분 판정을 도배. 반대급부로 FMR 68.8(default 62.4 대비↑)·Upd C 34.51↑는 custom 특유의 선별 효과.
6. **Ingest 83.7s/세션** — medium 사고로 think4(201.3s)보다 2.4배 빠르고 nano4(API 89.5s)와 동급. 로컬 120B가 API nano 수준의 처리량으로 훨씬 깨끗한 저장소를 만든 셈. (effort=high로 올리면 청결·갱신이 더 오를지, 시간만 늘지는 ablation 대상)

**한계**: A′/judge는 1유저(Martin)·oss120-high judge 레인 기준 — 절대값 인용 시 judge 병기 필수. 4u nano 그리드(§6) 편입은 base 레인 A′+nano judge를 추가로 돌리면 가능(산출물·경로는 준비돼 있음).

## 12. oss120 레인 12런 테이블 종합 판독 — 축 분해 (2026-07-30)

12런(백본 6종 × 프롬프트 2종) × Martin 1유저, gen=judge=gpt-oss-120b(high) 고정. 개별 런 서사가 아니라 **테이블을 지배하는 축**을 분해한다.

**① 프롬프트가 제1축 — 6백본 전부에서 같은 방향으로 작동하는 트레이드오프 스위치.** default→custom 델타의 부호 일관성: **Acc ↓6/6**(−27~−51pp, 예외 없음), **Upd C ↑6/6**(+8.5~+39.4), R ↑5/6(예외: think4 — 절제 붕괴로 R까지 잃음), FMR ↑5/6(예외: Qwen4B — custom인데 미끼까지 흡수), QA C ↓5/6(예외: full-traced→custom +2.4). 즉 custom은 "커버리지·갱신 완전성·미끼 저항을 사고 그라운딩·QA를 파는" 스위치이며, 이 방향성은 백본 선택보다 강하고 일관된 효과다.

**② QA를 끄는 건 R(완전 포함)이 아니라 '부분이라도 넓게'다.** 12런 스피어만: ρ(QA, WR−R 격차)=**+0.78**, ρ(QA, WR)=+0.55, ρ(QA, 추출 볼륨)=+0.55인 반면 **ρ(QA, R)=+0.16**에 불과. ρ(R, Acc)=−0.73의 커버리지-청결 트레이드오프가 저장 지표를 지배하지만, QA는 그 축과 비스듬한 제3축 — judge가 1점(부분 포함)으로 깎은 메모리도 답변 재료로는 기능한다는 뜻이다. "잘게 쪼개기"(default 전 백본에서 1점 60~70%)는 포함 점수엔 불리해도 QA엔 불리하지 않다. 부수 발견: ρ(QA, FMR)=−0.52(절제의 대가), ρ(QA, Upd C)≈0, ρ(QA, ingest 속도)≈0.

**③ QA 문항 구조 — 전멸 10%, 유니언 90%, 그 사이의 대혼전.** 공통 155문항 중 **15문항(9.7%)은 12세팅 전부 오답**, 14문항은 전승. 전멸 15문항은 개별 검증 결과 절반이 시스템 한계가 아니었다 (§13). 나머지 126문항이 변별 구간인데 난이도 분포가 거의 균일하다. 12세팅 중 하나라도 맞힌 문항의 유니언은 140/155=**90.3%** — 개별 최고가 60.4%인 것과 대비하면, 정답 여부가 세팅에 따라 크게 출렁인다(검색·생성 경로 민감성). QA C의 상위권 수 %p 차이가 노이즈인 이유가 여기 있다.

**④ 백본 축은 'reasoning 유무'에서 끝나고 크기는 잔차다 (수확 체감).** default 열에서: non-reasoning Qwen 4B/30B는 다작(1,286/1,334)+오염(Acc 72/83)으로 체급 7.5배가 무의미한 동형이고, reasoning군에선 초소형 API nano(848개, Acc 95.3)와 로컬 120B(825개, Acc 98.6)가 볼륨·포함분포(0/1/2점 25/64/11 ≈ 25/65/10)·QA(정답 90 vs 89/155)까지 쌍둥이다. 120B의 잔차 우위는 재작성 견고성(UPDATE-유래 Acc 96.4 vs nano 80.1) 하나. **백본 상향의 한계효용은 reasoning 전환에서 대부분 소진되며, 남은 병목은 파이프라인(프롬프트·검색·갱신 로직)이다.**

**⑤ 실패 구조 12런 완판 — custom은 병목이 '추출'에서 '검색·활용'으로 이동.** 실패 QA 중 추출 누락 비중: default군 51~64%, custom군은 낮아지는 대신(예: mini4-custom 24.6%) **"전부 완전 저장인데 오답"이 15~28%로 급증**(default군 4~11%). 문단형은 저장까진 시키는데 그 초장문에서 답을 못 꺼낸다 — full-custom 때 세운 "병목이 활용으로 이동" 결론이 6백본 전반으로 일반화됨. 예외적 붕괴는 think4-custom(추출 누락 71.4%).

**⑥ 지표 취사선택 가이드 (이 레인 기준).** 변별력 있는 지표: R(7.8~53.7)·Acc(40~99)·FMR(48.8~86.4)·Upd C(3.5~49.3). 주의 지표: **Target P는 custom 행들에서 모수가 4~24개로 붕괴**해 통계적으로 무의미(oss120b4의 TP 1위도 default 간 비교로만 유효), Upd H는 0~7건 희소라 Upd 지표는 사실상 C↔O 스펙트럼, 갱신 평가 모수는 전 런 142로 동일(비교 공정). QA C는 ③의 이유로 ±수 %p를 읽지 않는다.

## 13. 전멸 15문항 개별 검증 — "구조적 한계"의 절반은 벤치마크 결함 (2026-07-30)

§12③의 전멸 15문항에 대해 evidence의 **저장 여부(judge integrity)와 검색 여부(context 포함, 토큰 60% 매칭)를 12런 전수 대조**하고, 대표 문항의 답변·context 원문과 데이터셋 대화 본문까지 확인했다. 전멸 문항의 판정 구성은 H 106 : O 74 (H 58.9%)로 전체 평균(29.7%, 런별 23~40%)의 두 배 — "몰라서 못 답한" 것이 아니라 **무언가를 검색해 와서 자신 있게 틀렸다**는 신호이며, 검증 결과가 이를 확인해준다.

**① 검색 실패 확정 — 저장은 100%인데 검색이 0~17%** (s23/qa0 여행, s37/qa1 음료, s44/qa1 반려동물, 전부 Basic Fact Recall):
- s37/qa1: 2031년 골든("저당 탄산음료")이 **integrity 2점으로 저장돼 있는데 검색 context 20건에 0건** 포함. 대신 2025년 "Dislikes sugary sodas", 2027년 음료 기준 메모리가 자리를 채웠고, nano4는 그 구버전을 근거로 "Fresh smoothies"라 답했다.
- s23/qa0: nano4의 context에 2025년 **"Dislikes crowded tourist spots"(정반대 구버전)**가 검색됨. 저장소에는 2028년 갱신본이 있는데도.
- 기전: top-k 코사인 유사도는 **질문과 의미적으로 가까운 것**을 가져올 뿐 **시점이 맞는 것**을 가져오지 않는다. context 포맷에 `session_time:` 접두사가 있어 LLM은 날짜를 볼 수 있지만, 맞는 버전이 후보에 없으면 무의미하다. → **검색 계층의 시간 인지 부재**가 mem0-classic의 실증된 병목.

**② 벤치마크 결함 확정 3건** (시스템 성능과 무관하게 정답 불가):
- **s7/qa3** (골든 "Unknown", H12/12): 12런이 **전부 "No siblings mentioned."로 동일 답변**했고 전부 Hallucination 판정. 의미상 골든과 같은 답이 오답 처리된 **순수 채점 오류**. evidence 필드도 비어 있다. **judge 프롬프트 자체가 이 경우를 명시하고 있어 오류가 확정적이다** — QA 프롬프트 원문: 정답이 "unknown / cannot be determined"일 때 시스템이 단정적 사실을 답하면 Hallucination이지만, *"If the system also answers 'unknown' (without guessing), it may be Correct."* 즉 프롬프트의 규칙대로면 Correct여야 했다. judge 3종(nano·mini·oss120)이 모두 자기 지시를 어긴 셈이다.
- **s52/qa3** (골든 "From 20000 to 23000 yuan"): 이 수치가 **64세션 전체 대화 본문에 0회 등장**하고 persona_info에도 없다. 골든 메모리포인트로만 존재(s49, s60)하는 **구조화 프로필 필드의 변경 기록**이라 대화 기반 시스템은 원리적으로 답할 수 없다. 게다가 근거는 s49에 있는데 질문은 s52에 붙어 있다(세션 불일치).
- **s29/qa6** (골든 "Abnormal"): 상태 변화 MP는 **s26**에 있는데 질문은 s29. 시스템들은 "Overwhelmed, mental health challenged"로 의미상 맞는 답을 했으나 카테고리 라벨 불일치로 오답.

**③ 골든 정답의 요약 임의성** — s23/qa0에서 mini4·think4는 당해(2028) 메모리를 정상 검색했는데도 오답이다. 저장된 메모리가 "alternating crowded and remote destinations"인 반면 골든은 "crowded tourist spots for cultural enrichment" — 원 대화의 뉘앙스를 어느 쪽으로 요약했느냐의 문제지 기억 실패가 아니다. 사변형 문항 4~5건(s13/qa0 "다음에 들을 음악 → 앰비언트나 재즈" 등)도 같은 계열로, **근거 없는 추측을 거부한 행동(O 압도)이 감점되는** 구조다.

**④ 파괴적 UPDATE는 전멸 문항의 원인이 아니다 — 그리고 그건 방법론적으로 당연하다.** 나머지 9문항에 대해 근거 메모리의 추출→UPDATE/DELETE 생존을 12런 전수 추적한 결과, **근거가 이후 UPDATE로 소실된 비율 0~8%, DELETE 0%**. 추출률이 6~17%로 낮은 문항(s37/qa0, s21/qa3, s4/qa2, s52/qa5)은 "저장된 적 없음"(추출 실패)에 해당한다. 파괴적 UPDATE 가설이 여기서 검증되지 않는 이유는 가설이 틀려서가 아니라 **전멸 문항이 모든 세팅이 동시에 실패한 사례**이기 때문이다 — UPDATE 덮어쓰기 피해는 UPDATE를 많이 수행한 세팅만 실패하는 **세팅별 편차**로 나타나므로, 조합 비교 분석(정답이 갈린 문항군)에서 찾아야 한다.

**⑤ 근거 메모리가 질문 세션 밖에 있는 경우가 흔하다** (s21/qa3→s18, s21/qa6→s19, s52/qa5→s51, s7/qa5→s5, s52/qa3→s49, s29/qa6→s26). 질문이 속한 세션만 뒤지면 멀쩡히 저장된 근거를 "저장된 적 없음"으로 오분류하게 된다 — 정성분석 지침에 반드시 포함할 것.

**재분류 결과**: 전멸 15문항 = **검색·버저닝 한계 3~5문항** + **벤치마크 결함/채점 오류 확정 3문항** + **골든 임의성·사변형 의심 4~5문항** + **추출 실패 4문항** (파괴적 UPDATE 0문항). 즉 §12③의 "9.7% 구조적 한계"는 실질적으로 **2~3%의 검색 계층 한계 + 5% 내외의 벤치마크 노이즈**로 다시 읽어야 한다. 정성분석의 3분기(미저장/덮어씀/미검색)에는 **네 번째 분기 "애초에 답 불가 또는 채점 오류"** 를 반드시 추가한다.

## 14. ⚠ 무효 UPDATE (no-op) 발견 — "재작성 drift" 결론의 근본 정정 (2026-07-30)

정성분석 중 trace에서 발견된 제보(Qwen3-4B가 UPDATE 시 previous_memory를 그대로 되돌려줌)를 12런 전수 검증했다.

**측정 방법**: 병합 jsonl의 `memory_events` 중 `event=="UPDATE"`인 항목에서 `previous_memory`와 `memory`를 `.strip()` 후 비교 — 완전 일치=no-op, `difflib.SequenceMatcher` ≥0.95=근사동일, 그 외 실질 변경. 여기서 `previous_memory`는 mem0가 **벡터 스토어에 있던 기존 값**을 리턴에 담아준 것(DB 측 기록)이다.

| full-traced (Qwen3-4B) | 801 | **99.5%** (797건) | 0% | 4건 |
| full-custom | 214 | 90% | 3% | 7% |

**교차검증 3종** — 이 수치는 세 경로에서 독립적으로 확인됐다:

*(a) 원천 검증 (trace의 LLM 원본 응답).* mem0의 update 프롬프트는 UPDATE마다 `old_memory` 필드를 함께 요구하므로 **모델 응답 JSON 안에 신·구 텍스트가 같이 들어 있다**. mem0의 기록을 거치지 않고 이를 직접 파싱한 결과: full-traced 821항목 중 **97%** 가 `text == old_memory`, 30b4 91%, think4 3%, oss120b4·mini4 0%, nano4 12% — DB 측 기록과 모델 자기보고가 같은 결론이다 (수 %p 차이는 UPDATE 결정이 실제 쓰기로 이어지지 않은 항목 때문: 821건 결정 vs 801건 기록).

*(b) 다유저 검증.* Martin 1유저가 아니라 각 런의 전체 유저에서: **full-traced 20유저·UPDATE 19,752건에서 no-op 97.2%** (유저별 87~100%), 30b4 4유저 2,512건 96.9%(93~99%), nano4 13.9%(12~18%), think4 0.6%(0~3%), mini4 0.1%, oss120b4 0.0%. 표본 효과가 아니다.

*(c) 계측 아티팩트 배제.* 동일 코드 경로·동일 필드로 기록했는데 mini4·oss120b4는 0%가 나온다. 기록 로직의 버그였다면 전 런에서 같은 패턴이 나와야 한다.

**측정의 한계**: think4는 trace 파싱 10건이 실패했다(thinking 출력이 JSON 밖에 섞인 경우) — 70건은 정상 파싱돼 mem0 기록과 일치하나 분모가 미세하게 불확실하다. "완전 동일"은 문자열 기준이라 공백·구두점만 바뀐 경우는 실질 변경으로 분류되는데, 이를 잡는 ≥0.95 칼럼이 full-traced에서 0%이므로 결론에는 영향이 없다. 또한 이 수치는 "모델이 같은 텍스트를 되돌려줬다"까지만 말해주며, **그 원인**(프롬프트의 `old_memory`를 `text`에 복사하는 형식 오해인지, 갱신 내용을 생성하지 못한 것인지)은 프롬프트·응답 원문의 정성 확인 대상이다.

결론적으로 **계측 아티팩트가 아니라 non-reasoning Qwen 계열의 지시 불이행**이다. 파장이 크다:

**① "Qwen의 재작성 drift"는 존재하지 않았다 — 정반대다.** §8과 그리드 판독에서 "UPDATE-유래 Acc 20~21%(4B/30B)"를 재작성 품질 문제로 귀속했으나, 실제로는 **재작성을 아예 하지 않았다**. UPDATE-유래 Acc 56.2%(0점 24.5%)는 망가진 재작성본이 아니라 **갱신되지 않은 구버전이 후속 세션의 추출 목록에 재등록된 것**이며, 그 세션 대화에 근거가 없으니 0점을 받는다. 즉 **파괴적 UPDATE가 아니라 무효 UPDATE**가 Qwen 계열의 실패 모드다.

**② 볼륨 지표가 오염돼 있었다.** full-traced의 "1,286개 메모리"는 실제로 ADD 485개 + **no-op 재등록 800개**이고, 30b4의 1,334개도 절반가량이 중복이다. "Qwen 계열은 다작(6k)" "다작=오염" 프레이밍은 **재작성본을 새 메모리로 세었기 때문**이며, 실제 고유 메모리 수는 reasoning 백본들과 비슷하거나 오히려 적다. Acc 하락분의 상당 부분도 같은 원인(구버전이 엉뚱한 세션에서 채점됨)이라, **Qwen의 저장 청결도는 지금까지 과소평가돼 있었을 가능성**이 있다.

**③ 갱신 실패의 진짜 대가는 스토어 정합성이다.** no-op UPDATE는 mem0가 "이 사실은 갱신 대상"이라고 판정까지 해놓고 내용을 바꾸지 않으므로, **모순되거나 낡은 정보가 영구히 남는다**. Qwen 백본의 Upd O 92.3%(full-traced)는 이 구조의 직접적 귀결이다.

**④ reasoning이 갈랐다 — 같은 4B, thinking만 켰을 때 100% → 3%.** full-traced와 think4는 동일 모델 계열·크기이고 차이는 thinking뿐인데 no-op률이 100%에서 3%로 붕괴한다. 모델 크기는 무관하다(30B도 93% no-op). custom 프롬프트도 못 고친다(90~99%). **UPDATE 명령 이행은 스케일이나 프롬프트가 아니라 reasoning 여부가 결정한다** — §8 결론을 훨씬 강한 형태로 재확인한 셈이다.

**조치**: (a) 이 문서와 `mem0-halumem-baseline.md`에서 Qwen 계열의 "재작성 drift/과잉 재작성" 서술은 "무효 UPDATE"로 정정 필요, (b) 볼륨·Acc 비교 시 no-op 중복 제거본을 병기할 것, (c) 정성분석 카테고리 2는 "파괴적 덮어쓰기"와 "무효 갱신" 두 갈래로 나눠 판정할 것.

**종합**: 이 테이블에서 "지배적 백본"은 없다 — 1위가 지표마다 흩어진다(R/WR/F1=full-custom, Acc=think4, FMR=think4-custom, Upd C=mini4-custom, QA=트리오). 성능의 대부분은 ①프롬프트 축과 ④reasoning 축이 설명하고, QA 개선의 지렛대는 ②'부분 포함의 폭'과 ⑤검색·활용 쪽에 있다. (모든 수치는 1유저 표본 — 4유저 확장 배치로 재검 예정)

## 15. oss120 레인 4유저 확장 — 1유저 결론의 재검 (2026-07-31)

Stage A는 그대로 두고 **A′·judge만 첫 4유저로 확장**(gen=judge=gpt-oss-120b high, 12런). 산출물 `genoss120-4u/`, `judge-oss120-genoss120-4u-{run}/`. 무효율 58/74,212 = **0.078%**. 공통 705문항.

**① QA 순위 — 멤버는 바뀌었으나 "상위권은 구분 불가"는 유지.** 1유저에서 58.54로 트리오(nano4·mini4·30b4 60.37)에 밀렸던 oss120b4가 4유저에서 **61.28로 1위**가 됐다. 그러나 McNemar 검정 결과 상위 3개는 여전히 통계적으로 구분되지 않는다:

**② ⚠ 재생성 분산 21% — 절대 수치 신뢰도의 상한.** 1u 레인과 4u 레인은 **완전히 동일한 세팅**(같은 Stage A 메모리, 같은 generator·judge 설정)인데 A′를 다시 돌렸을 뿐이다. 그런데 Martin의 동일 문항에서 **판정이 21.0%(413/1,968) 바뀌었다.** 파장:
