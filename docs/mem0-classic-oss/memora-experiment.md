# Memora 벤치마크 실험 (mem0 classic OSS)

Memora(*From Recall to Forgetting*, ACL 2026 Findings)를 HaluMem·BEAM과 같은 스택에 얹어
재현하고 해부한 기록임. 데이터·코드 출처는 [github.com/geniesinc/Memora](https://github.com/geniesinc/Memora)
(Apache 2.0). 논문은 [aclanthology.org/2026.findings-acl.1337](https://aclanthology.org/2026.findings-acl.1337/).

HaluMem·BEAM과 나란히 놓지 않음. 벤치마크마다 자기 비교 공간을 가짐.

---

## 0-0. 지금까지 (3기간 전량, 2026-08-21)

**세운 것**

1. **저장소가 커지면 무너진다.** 페르소나당 저장 메모리 171 → 544 → 1,578개로 가는 동안
   전체 FAMA가 48.74 → 35.15 → 24.03으로 반토막 남 (§6-1)
2. **무너지는 방식이 과제마다 다르다.** `remembering`은 71.18 → 29.09로 직격이고,
   `recommending`은 51.70 → 37.99로 버팀. 취향은 반복 언급돼 중복 저장되므로 검색에
   걸릴 확률이 유지됨 (§6-2)
3. **FAA가 오르는 것은 개선이 아니다.** 52.32 → 63.35 → 72.69로 오르는데 같은 구간에서
   MPA는 60.57 → 33.04로 무너짐. 검색이 정답을 못 꺼내면 무효 항목도 같이 안 꺼내옴.
   문항 단위로도 MPA와 FAA는 반대로 움직이고(ρ −0.21 / −0.47 / −0.26), 답변 길이를
   통제해도 남음(편상관 −0.19 / −0.43 / −0.22) (§6-3)
4. **페널티가 줄어드는 것도 개선이 아니다.** 같은 이유임. quarterly 페널티 9.01은
   weekly 11.83보다 작지만, 꺼내온 것 자체가 없어서임 (§6-3)
5. **`reasoning`은 세 기간 모두 최하위이고 페널티가 0이다.** 23.33 → 8.00 → 5.00.
   이 과제엔 forgetting 기준이 없음(λ=0). 망각 벤치마크의 제일 큰 구멍이 망각이 아닌
   데 있음 (§6-2)
6. **삭제 개수는 맞추는데 대상은 모른다.** 발생비 96.9% → 104.9% → 107.8%로 100%를 넘어감.
   저장소가 커질수록 지우라고 하지 않은 것까지 지움 (§6-4)
7. **재실행 노이즈가 크다.** 같은 페르소나·같은 문항을 전 구간 다시 돌려 과제 FAMA가
   12.67 움직였음. 스모크의 "삭제 60%"는 재현되지 않고 90%가 나옴 (§6-6)

**아직 못 세운 것**

8. **페널티가 저장소 탓인지.** 삭제 발생비 대 FAA의 Spearman ρ가 +0.176 / −0.503 / −0.067로
   기간마다 부호가 뒤집힘. 이 대리지표로는 아무것도 말할 수 없음. 삭제 대상을 실제로
   짝지어야 함 (§6-7)
9. **`remembering` 붕괴가 검색 실패인지 저장 실패인지.** 정답 메모리가 저장소에 있는데
   top-50에 안 드는 것인지, 애초에 저장이 안 된 것인지 갈라야 함 (§7)

## 0. 왜 이 벤치마크인가

**HaluMem에도 BEAM에도 없는 것이 여기 있음: 삭제.**

우리가 지금까지 세운 것 중 제일 단단한 두 가지가 갱신에 관한 것임.

- 갱신 판정이 사람·LLM 양쪽에서 정렬돼 있지 않음 (사람끼리 Cohen κ 0.562, `backbone-experiment.md` §18-3)
- 무효 UPDATE가 99.5% (§14)

그런데 HaluMem은 삭제를 아예 안 재고, BEAM은 갱신 골든조차 없음. Memora는 **삭제를 19~21%
비중으로 넣고, 삭제된 것을 언급하면 점수를 깎음.** 우리 서사의 빈 칸을 정확히 메움.

| 벤치마크 | 통합 필요 세션 (평균/최대) | 갱신·삭제 (평균/최대) |
|---|---|---|
| LOCOMO | 1.3 / 15.0 | **0.0 / 0.0** |
| LongMemEval | 1.9 / 6.0 | 2.0 / 2.0 |
| PersonaMem | 1.3 / 3.0 | 1.2 / 3.0 |
| **Memora Weekly** | 5.3 / 26.0 | 2.7 / 11.0 |
| **Memora Quarterly** | **28.4 / 309.0** | **14.8 / 94.0** |

논문 Table 1임. LOCOMO는 문항의 94%가 두 세션 이하로 답이 나옴.

## 1. 데이터 (로컬 전수 실측)

```
data/{weekly|monthly|quarterly}/<persona>/
├── conversations/session_NNNN.json
└── evaluation_questions_<persona>.json
```

페르소나 10종은 직업군임 (`academic_researcher`, `software_engineer`, `startup_founder` 등).

| | weekly | monthly | quarterly |
|---|---|---|---|
| 페르소나 | 10 | 10 | 10 |
| 세션 | 1,551 | 6,150 | 19,913 |
| 턴/세션 중앙 | 15 | 15 | 15 |
| 문항 | 150 | 150 | 300 |
| 평가 기준 | 735 | 1,315 | 4,365 |
| λ 중앙 | 0.286 | 0.441 | 0.375 |

⚠ **논문의 기준 수(749 / 1,421 / 4,884)와 공개본이 다름.** 2~11% 적음. 공개본 차이로 보이며
수치를 인용할 때 밝혀야 함.

### 1-1. 연산 분포: 삭제가 갱신보다 많음

| | add | **delete** | update | 메모리 없는 세션 |
|---|---|---|---|---|
| weekly | 703 | **193** | 136 | 519 (33%) |
| monthly | 2,371 | **788** | 583 | 2,408 (39%) |
| quarterly | 7,434 | **2,178** | 2,102 | 8,199 (41%) |

세션의 33~41%가 메모리를 전혀 안 담는 **순수 잡음**임. 그리고 세션당 `share_memory: true`
턴이 중앙 1개임. 15턴짜리 대화에 기억할 것이 한 줄 들어 있는 구조임.

### 1-2. 스키마

**세션 파일.** `session_type`(activity/preference/goal/no_memory), `operation`(add/update/delete/null),
`operation_details`(구조화된 메모리 항목), `date`, `conversation[{turn, speaker, message, share_memory}]`.
speaker는 `user_agent` / `ai_agent`임.

**문항.** `question_id`, `question`, `question_date`, `memory_evidence`, `forgetting_evidence`,
그리고 `evaluation.evaluation_questions[]`. 기준 하나는
`{evaluation_question, expected_answer: yes|no, evaluation_type: memory_presence|forgetting_absence}`임.

**설계를 크게 단순하게 만든 실측 하나: `question_date`가 전부 기간의 마지막 날임.**
체크포인트 없이 전부 투입한 뒤 물어도 미래 정보가 새지 않음.

**추적이 됨.** `memory_evidence`·`forgetting_evidence`에 `session_id`가 붙어 있어 HaluMem
골든처럼 "어느 세션에서 들어온 사실인가"를 따라갈 수 있음.

## 2. FAMA

```
FAMA = max(0, MPA - λ · (1 - FAA))
  MPA = memory_presence 기준 충족 비율     (넣어야 할 것을 넣었나)
  FAA = forgetting_absence 기준 충족 비율   (빼야 할 것을 뺐나)
  λ   = N_forget / (N_presence + N_forget)   ← 문항마다 다름
```

과제 점수는 그 과제 문항 FAMA의 평균 × 100임.

**페널티가 셈.** presence 5 / absence 8 짜리 문항이면 λ=0.615라, **기억을 완벽히 하고 망각을
전부 실패하면 1.0이 0.385로 떨어짐.** 구현과 검산은 `src/memora/fama.py`.

## 3. 우리 레인 (이탈 대장)

**공식 수치를 재현하는 것이 목적이 아님.** 모델이 전부 다르므로 애초에 불가능함. 목적은
HaluMem·BEAM과 **같은 레인 안에서** mem0의 기억·망각 행동을 재는 것임.

어디가 왜 다른지를 구분해 적어둠. 나중에 어느 선택이 원칙이고 어느 것이 제약인지 헷갈리지
않게 하기 위함임.

| 항목 | 공식 | 우리 | 구분 |
|---|---|---|---|
| 메모리 백엔드 | Mem0 관리형 · v3 파이프라인 | **classic OSS 0.1.118** | 어쩔 수 없음 |
| 세션 시각 | `add(..., timestamp=<unix>)` | `metadata['session_date']` | **어쩔 수 없음** (OSS `Memory.add()`에 그 인자가 없음) |
| 답변 생성 모델 | gpt-4o-mini · `max_tokens=500` · `temperature=0.7` | gpt-oss-120b · effort high · **길이 제한 없음** | **우리 선택** |
| 채점 | GPT-4.1 + Claude Haiku 4.5 + Gemini 2.5 Flash 다수결 | gpt-oss-120b · effort high · 1회 | 자원 제약 |
| agent LLM | (명시 없음) | gpt-oss-120b · effort 기본(medium) | **우리 선택** |
| 투입 단위 | 세션 통째 `add()` | 동일 | 공식 따름 |
| speaker 매핑 | `user_agent`→user, `ai_agent`→assistant | 동일 | 공식 따름 |
| 검색 | top-50, 날짜 필터 없음 | 동일 | 공식 따름 |
| 답변·채점 프롬프트 | `memory_to_answer.py` 원문 | 동일 | 공식 따름 |
| 컨텍스트 포맷 | `N. {memory} (relevance: 0.87)`, **날짜 없음** | 동일 | 공식 따름 |

**우리 선택 두 개의 근거.**

전 구간 gpt-oss-120b high는 HaluMem·BEAM과 레인을 맞추기 위함임. 이 세 벤치마크의 결과를
서로 읽으려면 모델이 같아야 함.

**답변 길이 제한을 안 두는 것**은 §5에서 실측으로 정한 것임. 공식은 `max_tokens=500`으로
그냥 끊는데, 우리가 같은 짓을 하면 필요한 내용까지 날아가 전체 점수가 오히려 나빠짐.
길이는 통제할 변인이 아니라 **함께 보고할 값**으로 다룸.

> ⚠ **논문 수치와 절대 비교하지 않음.** BEAM에서 세운 규칙 그대로임. 논문 표는 맥락으로만
> 옆에 두고 비교 불가를 명시함.

## 4. 파이프라인

| 단계 | 스크립트 | 하는 일 |
|---|---|---|
| Stage A | `eval/mem0-classic-oss/memora/ingest_memora.py` | 세션 통째 투입 → 문항별 top-50 검색 저장 (+`--trace`) |
| Stage A′ | `.../answer_memora.py` | 검색 결과로 답변 생성 |
| Stage B | `.../judge_memora.py` | 기준별 yes/no 판정 → FAMA |
| 판독 | `src/memora/readout.py` | 수행률·과제별·페르소나별·상관·길이 |

실험 하나 = `--version` 문자열 하나. `results/mem0-classic-oss/memora-{version}/`,
`traces/mem0-classic-oss/memora-{version}/`, Qdrant 컬렉션 `memora_{version}_{persona}`로 파생됨.

⚠ **투입은 페르소나 단위 병렬임.** 페르소나 안에서는 세션이 순차라 `--max-workers`를
페르소나 수보다 크게 줘도 소용없음. 10페르소나에 워커 5면 두 파도로 끝남.

⚠ 컬렉션은 페르소나가 끝날 때마다 지움. BEAM에서 컬렉션이 180개까지 쌓여 Qdrant가 죽은 적이
있음. `MEMORA_KEEP_COLLECTIONS=1`로 남길 수 있음.

### 4-1. 모델 env (빼먹으면 404로 몇 시간을 태움)

`.env`의 `OPENAI_MODEL`은 HaluMem 백본(`Qwen/Qwen3-4B-Instruct-2507`)이고 8002에는 그 모델이
없음. 세 스크립트 모두 모델명을 env에서 읽으므로 **아래 셋을 반드시 명시함.**

| env | 값 | 무엇 |
|---|---|---|
| `MEM0_LLM_MODEL` | `openai/gpt-oss-120b` | mem0 agent LLM (추출·갱신 결정) |
| `ANSWER_MODEL` | `openai/gpt-oss-120b` | 답변 생성 |
| `JUDGE_MODEL` | `openai/gpt-oss-120b` | 채점 |

effort는 **agent만 기본값(medium), answer·judge는 high**임 (§3). `MEM0_REASONING_EFFORT`는
설정하지 않음. 기존 그리드와 통제를 맞추기 위함임.

실제로 `MEM0_LLM_MODEL`을 빼먹고 돌려서 `NotFoundError: The model
'Qwen/Qwen3-4B-Instruct-2507' does not exist` 가 재시도로 쌓인 적이 있음. 그래서
`scripts/memora/run_cutoff_sweep.sh`는 시작 전에 `/v1/models`를 조회해 모델이 실제로
떠 있는지 확인하고, 없으면 투입을 시작하지 않음.

## 5. 스모크 판독 (2026-08-21, weekly / academic_researcher)

158세션 · 15문항 · 81기준. 투입 13분 · 답변 2분 · 채점 2분.

> ⚠ **이 절의 수치는 본실행에서 재현되지 않았음.** 같은 페르소나·같은 15문항인데 삭제
> 12건이 18건으로, recommending FAMA가 27.33에서 40.00으로 움직였음. 판독 논리는 살아
> 있으나 **숫자는 §6을 봄.** 대조 표는 §6-6.

### 5-1. mem0는 삭제를 하긴 하는데 덜 함

| | 데이터셋 의도 | mem0 실제 |
|---|---|---|
| ADD | 71 | **183** |
| UPDATE | 11 | 39 |
| **DELETE** | **20** | **12 (60%)** |

저장 171개 = ADD 183 − DELETE 12로 정확히 맞음 (UPDATE는 개수를 안 바꿈).

추가가 2.6배인 것은 정상임. 세션에 지정된 연산은 하나지만 mem0는 15턴 대화에 섞인 부수적
사실을 전부 뽑음. **읽어야 할 값은 삭제·갱신 수행률임.**

### 5-2. 페널티가 실재함

| 과제 | FAMA | MPA | 페널티 |
|---|---|---|---|
| remembering | 70.03 | 77.00 | 6.97 |
| **recommending** | **27.33** | 63.33 | **36.00** |
| reasoning | 13.33 | 13.33 | 0.00 |
| 전체 | 36.90 | 51.22 | 14.32 |

`recommending`에서 **36점이 날아감.** `reasoning`의 페널티가 0인 것은 그 과제에
forgetting 기준이 없어서임 (FAMA = MPA).

### 5-3. 페널티는 대부분 저장소 탓임 (길이 통제 대조)

답변이 중앙 2,726자로 공식 예산(500토큰)의 1.4배였음. FAMA가 과다 포함을 벌주므로
**길이가 원인인지** 갈라야 했음.

생성을 손대지 않고 채점 직전에 500토큰(o200k_base)으로 자른 대조군을 돌림.
`--truncate-tokens 500`. effort를 낮추는 방법은 길이와 사고량이 함께 움직여 변인이 둘이 되고
HaluMem·BEAM의 high 통일도 깨지므로 쓰지 않음.

| 과제 | | FAMA | MPA | 페널티 |
|---|---|---|---|---|
| recommending | 원본 | 27.33 | 63.33 | **36.00** |
| | 500 절단 | 35.33 | 63.33 | **28.00** |
| remembering | 원본 | **70.03** | 77.00 | 6.97 |
| | 500 절단 | 54.46 | **60.00** | 5.54 |
| 전체 | 원본 | **36.90** | 51.22 | 14.32 |
| | 500 절단 | 34.38 | 45.56 | 11.18 |

**36점 중 8점만 길이 탓임. 28점은 남음.** 자르고도 MPA가 63.33 그대로인데 페널티만 줄었으니,
저장소에 무효 메모리가 실제로 남아 검색에 딸려 오는 것임. 삭제 수행률 60%와 맞물림.

그리고 `remembering`은 절단으로 **MPA가 77.0 → 60.0으로 무너짐**(15문항 중 9개가 잘림).
전체도 36.90 → 34.38로 나빠짐. **자르는 것이 이득이 아님.** §3의 "길이 제한 없음"을 대표값으로
정한 근거임.

> ⚠ 스모크는 페르소나 하나(15문항)임. **수치를 해석하지 않음.** BEAM에서 12대화 잠정값을
> 확정값으로 읽었다가 35대화에서 0.03~0.06이 내려간 적이 있음 (`beam-experiment.md` §4-1).

## 6. 전량 판독 (weekly / monthly / quarterly, 2026-08-21)

세 기간 모두 완주함. 페르소나 10명 고정, 기간만 7일 / 30일 / 90일로 늘어남.

답변 450건 전부 `finish_reason=stop`임. 잘려서 점수를 잃은 건은 없음.

### 6-1. 저장소가 9배가 되면 FAMA가 반토막 난다

| | weekly | monthly | quarterly |
|---|---|---|---|
| 저장/페르소나 | 171 | 544 | 1,578 |
| **FAMA** | **48.74** | **35.15** | **24.03** |
| MPA | 60.57 | 49.58 | 33.04 |
| FAA | 52.32 | 63.35 | 72.69 |
| 페널티 | 11.83 | 14.43 | 9.01 |

이 표에서 **FAMA와 MPA만 같은 방향으로 움직임.** FAA는 반대로 오르고 페널티는 갔다가
돌아옴. §6-3에서 이 셋이 같은 원인의 세 얼굴임을 보임.

### 6-2. 무너지는 방식이 과제마다 다르다

| 과제 | weekly | monthly | quarterly | | weekly MPA | quarterly MPA |
|---|---|---|---|---|---|---|
| remembering | 71.18 | 47.91 | **29.09** | | 79.81 | **35.10** |
| recommending | 51.70 | 49.55 | **37.99** | | 78.57 | 59.01 |
| reasoning | 23.33 | 8.00 | **5.00** | | 23.33 | 5.00 |

**`remembering`이 직격탄을 맞음** (71.18 → 29.09). MPA가 79.81에서 35.10으로 내려감.
"지난주에 커피에 얼마 썼지" 같은 문항인데, 정답이 저장소 어딘가에 있어도 1,578개 중
top-50에 들지 못함. 순수 검색 문제로 보임 (검증은 §7).

**`recommending`이 제일 잘 버팀** (51.70 → 37.99). MPA도 78.57 → 59.01로 덜 떨어짐.
취향은 여러 세션에서 반복 언급돼 중복 저장되므로 저장소가 커져도 검색에 걸릴 확률이
유지되는 것으로 보임. **대신 무효 취향도 같이 살아남음.** 세 기간 모두 페널티가 제일 큼
(26.86 / 32.15 / 21.03).

**`reasoning`은 세 기간 모두 최하위이고 페널티가 0임.** 이 과제에는 forgetting_absence
기준이 하나도 없어서(λ=0) FAMA가 MPA와 같아짐. **여기서 무너지는 것은 망각이 아니라
검색·추론임.** 망각 벤치마크를 돌렸는데 제일 큰 구멍이 망각이 아닌 데서 나옴.

> ⚠ `reasoning`의 FAA를 100으로 적으면 안 됨. `fama.py`가 forget 기준이 없을 때 1.0을
> 기본값으로 두는 것이지 잰 값이 아님. 전체 FAA도 이 1.0들을 섞으면 weekly가 68.85로
> 부풀고, 실제로 잰 문항만 쓰면 52.32임. `readout.py`와 대시보드 모두 후자로 고쳐둠.

### 6-3. FAA가 오르는 것도, 페널티가 줄어드는 것도 개선이 아니다

quarterly의 FAA 72.69는 weekly의 52.32보다 20점 높음. 페널티 9.01은 11.83보다 작음.
표만 보면 "규모가 커질수록 잘 잊는다"로 읽힘. **아님.**

같은 구간에서 MPA가 60.57 → 33.04로 무너짐. **검색이 정답을 못 꺼내오면 무효 항목도
같이 안 꺼내옴.** 무효 항목을 언급할 기회 자체가 줄어든 것이지 잊기를 잘하게 된 것이
아님. 페널티가 줄어드는 것도 같은 이유임.

문항 단위로 검정함. 두 지표는 서로 다른 기준 집합(memory_presence 대 forgetting_absence)에서
따로 계산되므로 수식상 묶여 있지 않음. 그런데도 반대로 움직임.

| | n | Spearman(MPA, FAA) | 답변 길이 통제 후 (편상관) |
|---|---|---|---|
| weekly | 98 | −0.214 | −0.193 |
| monthly | 100 | −0.469 | −0.432 |
| quarterly | 198 | −0.259 | −0.224 |

**세 기간 모두 음수이고, 답변 길이를 통제해도 그대로 남음.** 잘 꺼내온 문항일수록 무효
항목도 같이 딸려 옴. 그 반대도 성립함.

여기서 스모크 때 세웠던 길이 가설도 손봐야 함. §5-3의 절단 실험은 **한 답변을 잘랐을 때**
페널티가 준다는 관찰이었음(문항 내 조작). 그런데 **문항끼리 견주면 긴 답변일수록 FAA가
오히려 높음**: r(길이, FAA)가 +0.289 / +0.230 / +0.158임. 층위가 다른 두 관찰이라 모순은
아니지만, **길이로 문항 간 점수 차이를 설명하면 안 됨.**

읽는 규칙: **FAA와 페널티는 MPA와 함께만 읽음.** 단독으로는 방향조차 반대로 해석됨.

### 6-4. 연산 발생비: 개수는 맞추는데 대상은 모른다

| 연산 | weekly | monthly | quarterly |
|---|---|---|---|
| **DELETE** | 187/193 = **96.9%** | 827/788 = **104.9%** | 2,348/2,178 = **107.8%** |
| UPDATE | 347/136 = 255.1% | 1,488/583 = 255.2% | 3,959/2,102 = 188.3% |
| ADD | 1,906/703 = 271.1% | 6,271/2,371 = 264.5% | 18,132/7,434 = 243.9% |

스모크의 60%는 재현되지 않았고(§6-6), 전량에서는 100% 근처임. 그런데 이것을 "mem0가
삭제를 잘한다"로 읽으면 안 됨. 두 가지 이유임.

첫째, **이것은 수행률이 아니라 개수 비율임.** mem0가 낸 DELETE 이벤트를 데이터셋이
지목한 삭제 대상과 짝지어 확인하지 않았음. 개수만 맞고 엉뚱한 것을 지웠을 수 있음.

둘째, **기간이 길수록 100%를 넘어감**(96.9 → 104.9 → 107.8). 페르소나 단위로 보면
weekly에서 이미 최대 133%가 있었음. **지우라고 하지 않은 것까지 지운 것임.**
저장소가 커질수록 mem0의 갱신 결정 LLM이 기존 메모리와 충돌한다고 오판하는 빈도가
올라가는 것으로 보임 (검증은 §7).

ADD가 2.4~2.7배인 것은 정상임. 세션에 지정된 연산은 하나지만 mem0는 15턴 대화에 섞인
부수적 사실을 전부 뽑음.

### 6-5. 페르소나별: 폭만 보고 순위는 보지 않는다

| | weekly | monthly | quarterly |
|---|---|---|---|
| FAMA 범위 | 37.4~58.1 | 28.6~41.7 | 17.8~30.1 |
| **SD** | **7.03** | **5.27** | **4.27** |

SD가 줄어드는 것은 바닥에 몰리기 때문임. 그리고 §6-6에서 보듯 같은 페르소나를 다시
돌리면 과제 FAMA가 12.67 움직임. **페르소나 간 SD와 재실행 노이즈가 같은 자릿수임.**
페르소나당 문항이 weekly·monthly 15개, quarterly 30개뿐이라 그럼.

이 표는 분포의 폭을 보는 용도이고, **개별 페르소나 순위는 읽지 않음.**
페르소나별 수치는 대시보드 Memora 탭에 전부 있음.

### 6-6. 재실행 노이즈 (스모크 대 본실행, 같은 페르소나·같은 문항)

스모크와 본실행은 `academic_researcher`의 같은 158세션·같은 15문항을 투입부터 채점까지
전 구간 다시 돌린 것임. 설정도 같음. 따라서 두 값의 차이가 **파이프라인 전 구간 재실행
노이즈**임.

| | 스모크 | 본실행 | 차이 |
|---|---|---|---|
| DELETE 발생 | 12 / 20 (60%) | **18 / 20 (90%)** | **+6건** |
| ADD | 183 | 176 | −7 |
| UPDATE | 39 | 33 | −6 |
| 저장 메모리 | 171 | 158 | −13 |
| remembering FAMA | 70.03 | 65.60 | −4.43 |
| **recommending FAMA** | 27.33 | **40.00** | **+12.67** |
| reasoning FAMA | 13.33 | 13.33 | 0 |
| 전체 FAMA | 36.90 | 39.65 | +2.75 |
| 전체 MPA | 51.22 | 54.89 | +3.67 |

**스모크의 "삭제 60%"는 재현되지 않았음.** 같은 입력에 같은 설정인데 12건과 18건이 나옴.
추출·갱신 결정을 LLM이 하므로 투입 단계부터 흔들리고, 그 위에 답변 생성과 채점의
흔들림이 얹힘.

운영 규칙임.

- **페르소나 하나(15문항)짜리 수치는 어떤 것도 확정으로 쓰지 않음.** 과제 단위로 ±12점임
- 전체(150~300문항) 수준에서도 재실행 폭을 모름. 재실행을 안 해봤음
- §6-1의 기간 간 차이(FAMA 48.74 → 24.03, 24.7점)는 이 노이즈보다 훨씬 큼. 방향은 안전함
- BEAM에서 12대화 잠정값을 확정값으로 읽었다가 정정한 것과 같은 실수임
  (`beam-experiment.md` §4-1). 두 번째임

### 6-7. 삭제 발생비와 forgetting 정확도의 상관: 세 기간이 제각각

스모크 §5-3은 "페널티 36점 중 8점만 길이 탓이고 28점은 저장소에 남은 무효 메모리 탓"으로
읽었음. 페르소나 단위로 세 기간 모두 검정함.

| | weekly | monthly | quarterly |
|---|---|---|---|
| Spearman ρ (삭제 발생비 ↔ FAA) | **+0.176** | **−0.503** | **−0.067** |

**부호가 뒤집힘.** monthly만 보면 "삭제가 많이 난 페르소나일수록 forgetting이 나빴다"는
뜻이 되고, weekly는 반대이며, quarterly는 0임. n=10짜리 순위 상관 세 개가 이렇게 흩어지면
**이 대리지표로는 아무것도 말할 수 없음.**

원인은 x축에 있다고 봄. §6-4의 개수 비율은 대상 일치를 안 본 값이고, 100%를 넘는 초과
삭제와 미달 삭제가 한 숫자에 섞여 있음. 제대로 하려면 **삭제 대상을 짝지어야 함** (§7).

즉 §5-3의 저장소 귀인은 **확정도 기각도 못 한 상태**임. 다만 §6-3에서 MPA↔FAA 상충이
세 기간 모두 일관되게 나온 것은 별개의 단단한 관찰임.

### 6-8. 기간 간 비교가 가능한가

문항이 기간마다 다름. ID는 접미사만 다른데(`activity_food_coffee_158` 대 `_619`) 실제
문구가 바뀜.

| | stem 교집합 | 그중 문구까지 동일 |
|---|---|---|
| weekly(139) 대 monthly(146) | 74 | 27 |
| weekly(139) 대 quarterly(246) | 75 | 27 |
| monthly(146) 대 quarterly(246) | 82 | 26 |

세 기간 공통 stem은 71개임. 문구가 다른 예: `activity_todos`가 weekly에서는
"What tasks remain on my todo list this week?", monthly에서는 "...this month?"임.

결론: **문항 단위 페어링은 불가능하고, 기간별 집계 비교는 이 벤치마크의 설계 의도임**
(논문 Table 1이 Weekly/Quarterly를 나란히 놓음). 그래서 §6-1의 비교는 하되,
**차이를 특정 문항에 귀속하지 않음.** BEAM의 버킷 간 비교 금지(제목 겹침 0)와는
상황이 다름.

## 7. 남은 것

- **삭제 대상 짝짓기.** §6-4의 개수 비율을 실제 수행률로 바꿔야 함. 세션의
  `operation_details`가 지목한 대상과 mem0의 DELETE 이벤트 `text`를 매칭. 이게 되어야
  §6-7의 검정이 의미를 가지고, 100% 초과가 오삭제인지 확인됨
- **`remembering` 붕괴의 원인 분리.** 정답 메모리가 저장소에 있는데 top-50에 못 든
  것인지(검색 실패), 애초에 저장이 안 된 것인지(추출 실패), 지워진 것인지(오삭제).
  문항의 `memory_evidence`를 저장소 전체와 대조하면 갈림
- **`reasoning` 5.00의 원인.** 페널티가 0인데 제일 낮음. 여러 세션에 흩어진 사실을 엮는
  문항이라 flat top-50의 한계인지, 답변 프롬프트 문제인지 갈라야 함
- **재실행 폭 측정.** §6-6이 n=1이고 페르소나 하나임. 전량 기준으로 최소 2회는 돌려야
  SD를 말할 수 있음. 다만 quarterly는 투입만 13.5시간이라 weekly로 재는 것이 현실적임
- **top-k 늘리기.** 지금 top-50 고정임. quarterly에서 저장소가 1,578개인데 50개만 보므로
  3.2%만 후보임. k를 늘렸을 때 remembering이 회복되면 검색 실패가 확정됨
