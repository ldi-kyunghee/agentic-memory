# 단계별 오라클 상한 사다리 — 설계·구현·실행

> 작성 2026-08-03. 관련 판독: [backbone-experiment.md](backbone-experiment.md) §17
> **목적**: mem0 파이프라인의 각 단계를 차례로 "완벽한 정답"으로 대체하며 QA 상한을 재고, **구간 차이로 각 단계의 기여분을 분해**한다.

## 1. 왜 필요한가

지금까지 "병목은 추출 커버리지"라는 결론은 간접 증거(실패 QA의 43~60%가 evidence 미저장)로만 세웠다. 단계를 하나씩 오라클로 바꿔가며 QA를 재면 **어느 단계를 고쳐야 몇 점을 얻는지가 뺄셈으로** 나온다.

| 세팅 | 오라클로 대체한 단계 | QA C | QA H | QA O | 직전 대비 | 구간이 뜻하는 것 |
|---|---|---|---|---|---|---|
| 실측 (`oss120b4`) | — | **58.54** | 23.2 | 18.3 | | |
| **E1** (`oe1`) | 추출 | **65.85** | 18.9 | 15.2 | **+7.31** | ← 추출 커버리지의 몫 |
| **E2** (`oe2`) | 추출 + 갱신 결정 | **73.17** | 17.7 | 9.2 | **+7.32** | ← 갱신 로직의 몫 |
| 추출+갱신+검색 오라클 (`genoracle`) | 추출 + 갱신 + 저장·검색 | **83.54** | 3.0 | 13.4 | +10.37 | ⚠ 검색 기여로 읽으면 안 됨 (§6-2③) |
| 이론상 만점 | + generator·문항 | 100 | | | +16.46 | ← generator + 벤치마크 결함의 몫 |

**총 격차 25.0p.** 단 앞 두 구간(추출 7.3 / 갱신 7.3)만 조건이 완전히 통제된 비교이며, 마지막 구간은 컨텍스트 조건이 달라(evidence 평균 1.4개 vs 실제 top-20) 검색 기여의 **상한**으로만 읽어야 한다 — 판독은 §6-2.

## 3. 오라클의 정의 (해석에 직결)

**추출 오라클**: 그 세션의 골든 메모리 포인트를 fact 추출 결과로 주입한다. **미끼(interference)는 제외** — 완벽한 추출기라면 담지 않아야 하는 항목이기 때문이다. 부작용으로 FMR이 100 근처가 되므로 **FMR 비교는 이 실험에서 무의미**하다.

**갱신 오라클**: 각 골든에 대해 `is_update=True`면 저장소에서 `original_memories`와 가장 비슷한 항목을 찾아 UPDATE, 아니면 ADD로 결정한다. 매칭은 토큰 자카드 유사도 0.45 이상.

### 3-1. 갱신 골든의 원본(`original_memories`) 실태 — 오라클의 한계를 정하는 조건

Martin 기준, 갱신 골든 142건의 `original_memories`가 **선행 세션의 골든 MP로 실재하는지** 교차 집계:

| 기재된 원본 수 ＼ 실재 수 | 0 | 1 | 2 | 3 | 합계 |
|---|---|---|---|---|---|
| 1개 기재 | 85 | 23 | – | – | 108 |
| 2개 기재 | 8 | 8 | 14 | – | 30 |
| 3개 기재 | 2 | 0 | 1 | 1 | 4 |
| **합계** | **95** | **31** | **15** | **1** | **142** |

원본 항목 단위로는 **기재 180개 중 65개(36.1%)만 실재**한다.

**4유저 전체로 확장해도 방향은 같다** (Martin이 오히려 양호한 축):

| 유저 | 갱신 골든 | 기재 원본 | 실재 | 실재 0인 갱신 골든 | 실재 2+ (잔류 발생) | 잔류 메모리 |
|---|---:|---:|---:|---:|---:|---:|
| Martin Mark | 142 | 180 | 65 (36.1%) | 94 (66.2%) | 16건 | 17개 |
| 2번 | 162 | 185 | 33 (17.8%) | 140 (86.4%) | 10건 | 11개 |
| 3번 | 123 | 164 | 81 (49.4%) | 73 (59.3%) | 31건 | 31개 |
| 4번 | 168 | 205 | 47 (22.9%) | 136 (81.0%) | 15건 | 15개 |
| **합계** | **595** | **734** | **226 (30.8%)** | **443 (74.5%)** | **72건** | **74개** |

> 📌 **용어 확정** — 위 표와 교차표의 "실재 N"은 *기재된 원본 중 선행 세션 골든으로 존재하는 개수*이지 "기재된 것이 모두 존재"가 아니다. 예컨대 `기재 3 × 실재 2`는 셋 중 둘만 실재하는 경우이며 "실재 2+"에 포함된다. ("기재된 것이 전부 실재"로 세면 Martin 기준 38건.)
> "저장소에 없다"는 표현도 정확히는 **"선행 세션의 골든 MP 중에 그 원본 텍스트가 없다"** 는 뜻이다 — 추출 오라클에서는 골든이 곧 저장소라 결과가 같을 뿐이다.

여기서 세 가지가 따라온다.

**① 갱신 골든의 66.2%(Martin 94건 / 4유저 74.5%)는 원본이 저장소에 존재할 수 없다.** 기재된 원본이 선행 세션 골든에 하나도 없다는 뜻이고, 그 실체는 §17에서 확인한 **persona 프로필 필드 유래**다(예: `monthly_income "20000" → "23000"` — 이 수치는 64세션 대화에 한 번도 등장하지 않는다). 시스템은 물론이고 **오라클조차 갱신할 대상을 못 찾아 ADD로 처리**한다. 전 백본에서 Upd O가 높게 나오는 구조적 원인 중 하나다.

**② 실재 원본이 2개 이상인 16건은 현 오라클 구현에서 낡은 원본이 남는다.** mem0의 갱신 결정은 UPDATE 하나가 메모리 하나를 대체하는 구조이고, 현 구현은 가장 잘 맞는 원본 1개만 교체하므로 나머지는 저장소에 그대로 남는다(실측: oe2의 DELETE 연산 0건). 저장소 519개 중 최대 20개 안팎(≈4%)이며, 방향은 **E2를 과소평가**하는 쪽이다(낡은 원본이 top-20 검색을 오염시킬 수 있으므로).

**③ "완벽한 갱신"의 정의가 둘로 갈린다 — 보정 실험은 하지 않기로 확정.** (a) *mem0가 할 수 있는 최선* — UPDATE 하나로 하나를 교체. 현 구현. (b) *이상적인 저장소* — 갱신 시점에 superseded 원본을 모두 제거해 저장소가 항상 "현재 진실"만 담게 함. mem0의 갱신 결정 JSON이 `DELETE` 이벤트를 지원하므로 (b)도 구현 가능하다.

**결론: (b)는 구현하지 않는다.** 근거는 두 가지이고, 순서가 중요하다.

- **결정적 근거 — 갱신 단계 전체의 QA 기여가 측정 한계 이하다.** 5회 반복에서 E1→E2 = +1.46 (p=0.43), E1→E2pad = −0.24 (p=0.87)이다(§6-3). **갱신 단계를 통째로 완벽하게 만들어도 QA가 움직이지 않는데**, 그 안의 부분 보정이 SD 2.6p를 넘길 수 없다.
- **보조 근거 — 대상 자체가 작다.** 잔류 메모리는 Martin 17개 / 저장소 519개 = **3.3%** (4유저 74개).

> ⚠ 흔한 오해: *"대부분 원본이 실재하지 않으니까 잔류가 무해하다"* 는 **틀린 논증**이다. 잔류가 발생하는 72건은 **정의상 실재 원본이 2개 이상인 경우**이므로 그 안에서 남는 원본들은 실재한다. 원본 부재율이 설명하는 것은 *왜 잔류 케이스가 595건 중 72건(12%)뿐인가*이지, 그 72건이 무해한 이유가 아니다.

> ⚠ 보류의 범위는 **QA 기준**이다. 공식 update judge 프롬프트의 Correct Update 조건에는 *"The original memory is effectively replaced or marked as outdated"* 가 포함되므로(`HaluMem/eval/eval_tools.py:189`), 잔류 원본은 **Upd C 지표는 깎을 수 있다.** 사다리는 QA C만 읽으므로 §6-3의 결론에는 영향이 없다.

> 📌 **데이터셋 명세의 공백** — HaluMem 스키마 문서는 `original_memories`를 *"Previous related memories (if updated)"* 한 줄로만 정의하며, **원본이 여러 개일 때 몇 개를 덮어쓰고/지우고/보존해야 하는지에 대한 지침이 없다.** 채점 프롬프트에 "원본이 대체되어야 한다"는 문장이 있을 뿐이다. 즉 이 지점은 우리 구현의 선택이 아니라 **벤치마크 명세가 열어둔 자유도**다.

> 러너는 `update_miss` 카운트를 출력하므로 ①의 규모를 실행 로그에서 확인할 수 있다.

## 4. 구현 (mem0 코드 무수정)

mem0 0.1.118의 `_add_to_vector_store`는 두 번의 LLM 호출로 이뤄진다.

| 호출 | messages 형태 | 반환 | 오라클 대체 |
|---|---|---|---|
| fact extraction | system + user | `{"facts": [...]}` | 세션 골든(미끼 제외) 주입 |
| update decision | user 1개 | `{"memory": [{id,text,event,old_memory}]}` | 정답 ADD/UPDATE 결정 주입 |

**system 역할의 유무로 두 호출을 구분**할 수 있다 (기존 `TracingLLM`이 이미 쓰는 방식). 따라서 LLM 래퍼 하나로 mem0 내부를 건드리지 않고 주입할 수 있다.

### 4-1. `src/mem0-classic-oss/oracle.py` (신규)

- `OracleLLM(inner, extraction=, update=)` — mem0의 LLM 인스턴스를 감싼다.
- `set_session(memory_points)` — 러너가 `memory.add` 직전 호출. 미끼 제외 후 facts 구성, `is_update` 골든의 `original_memories` 맵 구축.
- `parse_old_memories(prompt)` — update 결정 프롬프트에 파이썬 repr로 박혀 있는 기존 메모리 목록(`[{'id':'0','text':...}]`)을 백틱 블록에서 `ast.literal_eval`로 복원. 기존 메모리가 없으면 빈 목록.
- `stats` — `{sessions, facts, add, update, none, update_miss}` 조작 점검용.

### 4-2. `eval/mem0-classic-oss/eval_memzero_oss.py` (수정)

- `from oracle import OracleLLM`
- `process_user`: `memory.delete_all` 직후 env 플래그를 보고 `memory.llm = OracleLLM(memory.llm, ...)`. **TracingLLM보다 먼저 감싼다** — 그래야 `TracingLLM(OracleLLM(llm))` 순서가 되어 주입된 응답이 trace에 그대로 남고, 나중에 "무엇을 정답으로 넣었는지" 검증할 수 있다.
- 세션 루프: `memory.add` 직전에 `oracle.set_session(session["memory_points"])`
- 유저 완료 시 `[oracle:{user}] {stats}` 출력, `main` 시작 시 `oracle 단계: ...` 출력

### 4-3. 검증 결과 (실데이터 단위 테스트)

| 항목 | 결과 |
|---|---|
| 추출 오라클 — 미끼 제외 | 골든 11개(미끼 2) → 9개 주입 ✅ |
| 추출만 켰을 때 갱신 호출은 실제 LLM 통과 | ✅ |

| 빈 저장소(첫 세션) | 15건 전부 ADD ✅ |

## 6. 대시보드 반영

**Metrics 탭 최상단에 "단계별 오라클 상한 사다리" 카드**가 자동으로 뜬다. 각 행은 추출·갱신·저장검색 3칸이 `오라클`(보라) / `실측`으로 표시되고, QA C 막대와 **직전 단계 대비 증가분**이 붙는다. 아직 안 돌린 단계는 `미실행`으로 흐리게 표시되다가 산출물이 생기면 자동으로 채워진다.

정의는 `src/web-dashboard/runs.yaml`의 `oracle_ladder:` 섹션 한 곳에만 있고, 계산은 `/api/oracle-ladder`가 공식 집계 함수를 재사용한다. 유저 범위는 Metrics 탭의 "유저 범위" 선택을 따른다 (사다리는 Martin 1유저 기준으로 설계됨).

## 6-2. 판독 (2026-08-03)

**조작 점검 — 오라클이 실제로 걸렸다.**

| 런 | 저장 메모리 | 평균 길이 | 연산 | 골든 원문 일치 |
|---|---|---|---|---|
| 실측 `oss120b4` | 825 | 78자 | ADD 618 / UPD 207 / DEL 7 | — |
| E1 `oe1` | 486 | 122자 | ADD 399 / UPD 87 / DEL 12 | 91.4% |
| E2 `oe2` | 593 | 117자 | ADD 519 / UPD 74 / DEL 2 | **100%** |

미끼 제외 골든이 정확히 **593개**인데 E2의 저장물이 593개·전부 골든 원문과 일치한다 — 추출·갱신을 모두 오라클로 덮으면 저장소가 "정답 그 자체"가 됨이 확인된다. E1이 486개로 더 적은 것은 **실제 갱신 결정이 일부 골든을 UPDATE로 흡수(87건)하거나 DELETE(12건)했기 때문**이며, 이 손실이 곧 아래 ②의 7.3점이다.

> ⚠ **아래 ①~⑤는 단일 회차 판독이며 상당 부분이 노이즈였다. 결론은 §6-3(5회 반복)을 따른다.** 이 절은 "단일 회차로 무엇을 잘못 읽었는가"의 기록으로 남긴다.

**① 추출 오라클: +7.31 (58.54 → 65.85)** — 완벽한 추출로 얻는 몫. 예상보다 작다. §12⑤·§13에서 "실패 QA의 43~60%가 추출 누락"이라 관측했으나, **추출을 완전히 고쳐도 QA는 7점밖에 오르지 않는다.** 저장 자체는 됐어도 뒤 단계(갱신·검색)에서 다시 잃기 때문이다. *(→ 5회 반복 실제값 **+11.58**. "7점밖에"라는 판단 자체가 틀렸다.)*

**② 갱신 오라클: +7.32 (65.85 → 73.17)** — 추출과 정확히 같은 크기다. *(→ 5회 반복 실제값 **+1.46, p=0.43로 유의하지 않음.** "동등한 크기"는 우연의 일치였다.)*

**③ 검색 구간 +10.37 (73.17 → 83.54) — ⚠ 이 값은 검색의 기여로 읽으면 안 된다.** 마지막 행은 "완벽한 검색"이 아니라 **정답 근거만 남기고 나머지를 전부 제거한** 조건이다. 실측치로 확인하면:

| | 컨텍스트 항목 수 |
|---|---|
| 실제 검색 (E2 포함 전 행) | top-20 고정, 평균 **19.9개** |
| 검색 오라클 행 | evidence만, 평균 **1.42개** (0개 39문항 / 1~2개 100문항 / 3개 이상 25문항) |

즉 이 구간에는 **(a) 맞는 항목을 찾아오는 능력**과 **(b) 무관한 19개를 치워 컨텍스트를 짧고 깨끗하게 만드는 효과**가 섞여 있다. **따라서 +10.37은 검색 개선으로 얻을 수 있는 몫의 상한이며, 실제 검색 기여분은 이보다 작다.** *(→ ⑤의 패딩 대조군으로 분리 측정한 결과 (a)는 **0에 가깝고 +11.10이 전부 (b)**였다. 이 경고는 옳았다.)*

추가로 **합성 데이터셋 특유의 유리함**이 있다. 골든 정답은 바로 그 evidence로부터 만들어졌으므로, evidence를 그대로 건네는 것은 "완벽한 검색"이 아니라 **정답의 출처를 직접 넘겨주는 것**에 가깝다. 게다가 그 evidence·정답의 품질 자체가 검증 대상인 상황이다(§13: 12세팅 전멸 문항의 상당수가 정답 임의적·답변 불가). 이 행을 "달성 가능한 상한"으로 인용할 때는 이 두 겹의 낙관을 명시해야 한다.

**⑤ 다음 실험 — 검색 기여분의 분리 측정** → **실행 완료.** `ANSWER_ORACLE_PAD`로 패딩 대조군을 만들고, 동시에 generator·judge 변동성을 걷어내기 위해 **전 행 5회 반복**으로 재측정했다. 결과는 §6-3.

⚠ 당시 남긴 단서 — *"7.3 대 7.3의 동률은 우연일 수 있다"* — 는 **맞았다.**

## 6-3. 판독 (2026-08-06 · 1유저 5회 반복)

> ⚠ **이 절의 ②·③은 §6-5에서 정정됐다.** 갱신 기여는 4유저에서 유의해졌고(ns → p=0.0014), 검색 구간 판단의 근거였던 E2pad 대조군은 버그로 무효였다. 확정 판독은 **§6-5**를 따른다.

각 행마다 **A′ 답변 생성 + judge 채점을 5회 새로** 돌린 평균±표본표준편차. Martin 1유저·질문 164개, agent=gpt-oss-120b(medium), gen=judge=gpt-oss-120b(high) 고정.

**① 추출이 유일한 실제 병목이다 — +11.58p, 총 격차의 52%.** 단일 회차의 "+7.31, 예상보다 작다"는 판단은 철회한다.

**② 갱신과 검색 정확도의 기여는 합쳐서 0이다.** E1 → E2pad를 직접 비교하면 **−0.24p (t=−0.16, p=0.87)**. 즉 **추출을 완벽하게 만든 뒤 갱신과 검색까지 추가로 완벽하게 만들어도 얻는 것이 없다.**
- 갱신이 0인 이유는 §3-1에 있다: 갱신 골든의 **74.5%(4유저)** 가 원본이 저장소에 존재조차 하지 않는 프로필 필드 유래라, "완벽한 갱신"이 바꿀 것이 애초에 거의 없다.
- 검색 정확도가 0인 이유는 오라클 저장소에서는 top-20이 이미 정답 근거를 잡아오기 때문이다.

**③ 마지막 +11.10p는 검색이 아니라 컨텍스트 축약 효과다.** E2pad는 정답 근거를 **이미 보장**하고 top-20으로 패딩만 한 조건이므로, E3와의 유일한 차이는 컨텍스트 크기(1.4개 vs 20개)뿐이다. 이는 **메모리 시스템의 능력이 아니라 "생성기에게 정답만 주고 나머지를 치웠을 때의 이득"**이다. 패딩 대조군이 없었다면 검색 기여를 11p로 과대보고했을 것이다.

**④ 저장소 측 부수 발견 — 완벽한 추출도 8.65%는 저장까지 못 간다.** E1의 R=91.35, E2(갱신 오라클)의 R=100. 차이 8.65%p는 **전부 갱신 결정이 골든을 흡수·삭제해 날린 몫**이다. 그런데 그것이 QA로는 +1.46(ns)밖에 되지 않는다 — **날아간 메모리가 QA에 쓰이지 않는 것들이라는 뜻.** 저장소 지표(R)의 개선이 최종 성능으로 이어진다는 보장이 없음을 보여주는 사례다.

**⑤ 갱신 능력 단독 측정** — E1의 Upd C=78.17은 실측 8.45와도, E2의 99.30과도 확연히 다르다. **추출이 완벽할 때 백본의 갱신 능력**을 단독으로 잰 값이며, 사다리 행 중 유일하게 Upd 지표가 유효한 지점이다.

**⑥ 노이즈 바닥 — 이 실험의 부산물이자 가장 광범위한 함의.** generator+judge를 재실행한 것만으로 **SD 2.2~2.9p, 회차 간 폭 최대 6.7p**가 나왔다. 백본 그리드 상위권(oss120b4 61.28 / nano4 59.43 / mini4 58.72, 4유저)의 간격은 이보다 작다. **단일 회차 수치로 5p 미만의 행 간 차이를 해석해서는 안 된다.**

**종합 — 말할 수 있는 것과 없는 것 (개정)**

말할 수 있는 것:
- **추출이 유일하게 유의한 단일 단계 병목이다** (+11.58, p=0.0001).
- **추출 이후 갱신·검색을 완벽하게 만들어도 QA는 오르지 않는다** (E1→E2pad −0.24, p=0.87). 조건이 완전히 통제된 비교다.
- 갱신 기여가 0인 것은 mem0의 결함이 아니라 **벤치마크 구조** 때문이다 — 갱신 골든의 74.5%가 대화에 없는 프로필 필드에서 파생돼 원본이 저장될 수 없다(§3-1).
- **완벽한 추출도 8.65%는 저장 단계에서 잃지만, 그 손실은 QA에 거의 영향이 없다.**

말할 수 없는 것:
- **"검색이 병목"** — 순수 검색 정확도 기여는 −1.71 (ns)로 측정됐고, 마지막 +11.10은 컨텍스트 축약 효과다.
- **"갱신은 중요하지 않다"** (일반화 금지) — 이 벤치마크에서 갱신 골든의 원본이 대부분 저장 불가능해 측정되지 않았을 뿐이다. 원본이 실재하는 데이터셋에서는 다를 수 있다.
- **4유저 일반화** — 아직 Martin 1유저 표본이다. 단 §3-1의 원본 부재율은 4유저 전체에서 확인했고(59~86%, 전체 74.5%) Martin이 오히려 양호한 축이므로, ②의 방향은 뒤집히지 않을 가능성이 높다.

| 단계 | QA C | SD | 구간 증가 | Welch t-검정 | 1유저 5회 |

### 정정 ① — 갱신 기여는 0이 아니다 (작지만 유의)

§6-3②에서 *"갱신과 검색 정확도의 기여는 합쳐서 0"*, *"갱신 단계를 통째로 완벽하게 만들어도 얻는 게 없다"*고 썼다. **1유저 표본에서 ns(+1.46, p=0.43)였던 것이 4유저에서 +2.55 (p=0.0014)로 유의해진다.** 표본 부족이었다.

다만 크기는 **추출(+12.37)의 1/5**이고, 갱신 기여의 상한 자체가 §3-1의 이유로 눌려 있다 — 갱신 골든의 74.5%는 원본이 저장소에 존재할 수조차 없어 "완벽한 갱신"이 바꿀 대상이 없다. 그러니 **"갱신은 중요하지 않다"가 아니라 "이 벤치마크가 갱신을 거의 측정하지 못한다"** 가 정확한 진술이다.

### 정정 ② — 🔴 E2pad 대조군은 버그로 무효였다

E2pad가 E2보다 **−6.64p (5회 전부 66~69, SD 0.97)** 로 나왔다. 정답 근거를 *추가*했는데 낮아지는 것은 구조상 불가능하므로 추적한 결과:

```
검색 context 항목 : "Sep 04, 2025, 18:42:18: Martin Mark's birth date is 1996-08-02"
evidence 항목     : "Martin Mark's birth date is 1996-08-02"          ← 시각 접두사 없음
```

`gen_answers.oracle_context()`가 evidence를 **접두사 없는 원문**으로 끼워넣고, dedup이 같은 내용의 *시각 붙은* 항목을 제거했다. 결과적으로 **정답 근거만 시각 정보를 잃고 낡은 방해 항목들은 시각을 유지**한다 — §13에서 *"top-k는 의미적으로 가까운 것을 가져올 뿐 시점이 맞는 것을 가져오지 않는다"*고 확정한 바로 그 축이, 정답 쪽에서만 무력화된 것이다. E3(근거만)이 멀쩡한 이유도 같다: 거기엔 시각 붙은 경쟁자가 아예 없다.

**수정**: evidence를 검색 context에 실렸던 `시각: 원문` 문자열로 복원한다. 이 유저의 검색 context 어딘가에 실린 원문이 있으면 그대로 재사용(실측 커버리지 **95.3%**), 없으면 골든 MP의 `timestamp`로 합성(mem0 저장 시각과 44~150분 차이라 세션 간 순서는 보존). 수정 후 접두사 없는 항목 **0%**, 컨텍스트 규모 평균 19.87항목으로 E2(19.91)와 일치.

**영향**: 1유저의 −1.71(ns)도 같은 버그라 함께 무효다. 즉 **"순수 검색 정확도의 기여 ≈ 0"이라는 §6-3②·③의 근거는 사라졌다.** 현재 말할 수 있는 것은 **E2 → E3 = +10.27 (검색 정확도 + 컨텍스트 축약의 합계)** 뿐이며, 분해는 재측정 후로 미룬다.

> ⚠ §6-3③의 *"마지막 +11.10p는 검색이 아니라 컨텍스트 축약 효과"* 라는 결론도 **E2pad에 의존하므로 함께 보류**한다. 방향(축약 효과가 상당하다)은 여전히 그럴듯하지만, 지금은 측정된 바가 없다.

## 6-4. 4유저 확장 (2026-08-07 · 중간 기록)

Stage A는 유저 단위 캐시(`tmp/{uuid}.json`)가 있어 `--user-num 4`로 재실행하면 Martin은 `skip (cached)`로 건너뛴다 — **1유저 저장소가 비트 단위로 보존**되므로 두 결과의 연속성이 보장된다. A′·judge는 `-4u-` 접두 디렉토리로 분리했다(같은 디렉토리에 `--regen`하면 답변은 새로 생성되는데 judge는 유저 캐시로 건너뛰어 **답변과 채점이 어긋난다**).

또한 E3(근거만) 행의 carrier run을 `full-traced`(Qwen3-4B 저장소) → **`oss120b4`** 로 옮겼다. 이 레인은 검색 컨텍스트를 쓰지 않고 evidence만 보므로 QA C는 저장소와 무관하지만, 사다리 맨 윗행과 아랫행이 다른 저장소를 쓰던 것은 **표시 문제가 아니라 설계상 비일관성**이었다. 이제 E3는 실측 행의 엄밀한 ablation이다 — *저장소 동일, 답변 입력만 다름*.

| 실측 | 59.52 ±0.41 | 5회 | – | 61.22 |

| E3 근거만 | 84.71 ±1.24 | 5회 | +10.95 | +11.10 |

**1유저 결론이 유지된다.** 추출 구간이 압도적이고(+13.67), **갱신 구간은 +0.57로 1유저(+1.46)보다도 작다.** §3-1에서 나머지 3유저의 원본 부재율이 Martin(66.2%)보다 높게(81~86%) 나온 것과 정합적이다 — 원본이 저장될 수 없을수록 "완벽한 갱신"이 바꿀 게 없다.

E1의 저장소 측 지표도 정합적이다: `R=90.44`·`Upd C=82.18` (1유저 91.35·78.17). **완벽한 추출도 9.6%는 저장까지 못 간다**는 §6-3④의 관측이 4유저에서도 같은 크기로 재현된다.

⚠ E1·E2는 아직 1회 실행이라 구간 증가에 검정을 붙일 수 없다. E2pad와 함께 5회 반복이 채워지면 갱신 구간의 유의성을 4유저에서 확정한다.

## 7. 해석 시 주의

1. **원칙은 QA C만 읽는다.** 단 단계별로 예외가 있다 — 아래 2 참조.
2. **어떤 지표가 죽고 어떤 지표가 사는지는 단순한 계단이 아니다.** 오라클을 넣으면 그 단계의 *내용 품질* 지표는 자명해져 죽지만, *생존율* 지표(R·Weighted R)와 *다음 단계* 지표(Upd)는 오히려 그 단계만 단독으로 재게 되어 살아난다. 대시보드는 이 규칙대로 `–` 처리한다(`app.py`의 `ORACLE_MASK`).

   | 행 | Acc·Target P·FMR·F1 | R·Weighted R | Upd C/H/O | QA |
   |---|:---:|:---:|:---:|:---:|
   | 실측 | ✓ | ✓ | ✓ | ✓ |
   | E1 추출 오라클 | **–** 저장물이 골든 원문이라 자명 | ✓ **유효** — 완벽한 추출이 저장까지 살아남은 비율(=갱신 손실 단독 측정) | ✓ **유효** — 추출이 완벽할 때의 갱신 능력 | ✓ |
   | E2 추출+갱신 | – | **–** 정의상 100 | **–** 정의상 ~100 | ✓ |
   | E2pad · E3 검색 | – | – | – | ✓ |

3. **FMR 비교 금지** — 오라클 추출이 미끼를 원천 제외하므로 "흡수하지 않은 비율"이 무의미하다.
4. **오라클 행의 살아있는 값도 백본 순위표에 넣지 않는다.** E1의 R=91.35는 열 최고값이지만 백본 능력이 아니라 주입된 정답이 만든 수치다. 대시보드는 이 값들을 표시하되 순위·최고값 계산에서 제외한다(기울임+보라색 표기).
5. **E2 이하는 백본 무관**하다. 추출·갱신 모두 오라클이면 LLM 호출이 사라져 순수한 "저장소+검색"의 상한이 된다. 백본 영향을 받는 것은 E1뿐(갱신 결정만 실제 LLM).
6. **단일 회차 수치로 구분 한계 미만의 차이를 해석하지 않는다** (§6-3⑥). generator+judge 재실행만으로 1유저 SD 2.2~2.9p, 4유저 0.8p가 나온다.
7. **반복 회차의 SD를 그대로 믿지 않는다.** 한 루프 안에서 연속 실행한 회차들은 서버 상태를 공유해 독립 시행이 아니며, 흔들림을 과소평가한다 — 4유저 실측에서 배치 내부 ±0.41 vs 배치 간 포함 ±0.81. 대시보드는 보수적인 쪽을 신뢰 밴드로 쓴다. 자세한 근거·규약은 `backbone-experiment.md` §17-4.
4. **1유저 표본**이다. §15에서 확인했듯 QA C 수 %p 차이는 노이즈일 수 있으므로, 구간 폭이 크게 벌어지는 경우에만 결론으로 삼는다.
5. **judge 자기 비일관성**(§17-2: QA 다수결 이탈 3.8%)이 각 행에 얹혀 있다. 3~4점 이내의 구간 차이는 판정 노이즈와 구분되지 않는다.
