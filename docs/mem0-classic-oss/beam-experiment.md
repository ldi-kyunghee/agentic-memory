# BEAM 벤치마크 실험 (mem0 classic OSS)

BEAM(*Beyond a Million Tokens*, ICLR 2026)을 HaluMem과 같은 스택에 얹어 재현하고 해부한 기록임.
데이터·코드 출처는 [github.com/mohammadtavakoli78/BEAM](https://github.com/mohammadtavakoli78/BEAM) 커밋 `3e12035`
(코드 MIT / 데이터 CC BY-SA 4.0).

HaluMem 실험과 나란히 놓지 않음. 벤치마크마다 자기 비교 공간을 가짐.

---

## 1. 왜 이 벤치마크인가

HaluMem에서 세운 결론은 "절대 수치가 judge와 프로토콜에 지배된다"였음. BEAM에서는 그 현상이
**이미 공개된 숫자에서 벌어져 있음.**

mem0가 발표한 BEAM 점수는 1M에서 **64.1**, 10M에서 **48.6**임. 논문 최고 베이스라인(LIGHT)은
1M에서 **0.336**임. 지표 계열은 같은데(둘 다 nugget 평균 × 100) 두 배 가까이 벌어짐. 확인해보니
프로토콜이 최소 다섯 군데 다름.

| 항목 | 논문 | mem0 발표본 |
|---|---|---|
| 답변 생성 모델 | GPT-4.1-nano / Qwen2.5-32B / Gemini-2.0-flash / Llama-4-Maverick | gpt-5 |
| judge 모델 | gpt-4.1-mini | gpt-5 |
| judge 프롬프트 | `unified_llm_judge_base_prompt` | 자체 재작성본 |
| 컨텍스트 | RAG 베이스라인 top-5 pair chunk | 메모리 top-200 |
| event_ordering 집계 | `tau_norm` | nugget 평균 |
| 백엔드 | 해당 없음 | Mem0 Cloud (시맨틱 + BM25 + entity boost) |

mem0의 OSS 백엔드용 Dockerfile은 `mem0ai @ git+.../mem0.git@feat/v3-pipeline`을 설치하는데
**그 브랜치가 현재 404임.** 즉 그 수치는 우리가 재현 중인 classic OSS 0.1.118도 아니고,
릴리스된 어떤 버전도 아니며, OSS 경로로는 재현 불가능함.

## 2. 설계

### 2-1. 데이터 구조와 HaluMem의 차이

| 항목 | HaluMem | BEAM |
|---|---|---|
| 최상위 단위 | 유저(uuid) | 대화(`100K_1`) |
| 그 아래 | 세션 | 배치 3~5개 (100K 실측) |
| 시각 정보 | 세션마다 `start_time` | **배치당 `time_anchor` 1개** (100K 전체 메시지 5,732개 중 90개, 1.57%) |
| 골든 메모리 | 세션마다 있음 | **없음** |
| 잴 수 있는 지표 | R, Acc, Upd, QA 4종 | **QA 하나** |
| 문항 구분 | 세션 안 QA | **능력 10종** |

골든 메모리가 없어 Integrity·Accuracy·Update를 못 잼. 대신 문항마다 어떤 능력을 묻는지가
라벨로 붙어 있어, HaluMem에서 못 하던 **능력별 분해**가 가능함.

**`chat.json`의 실제 모양** (100K_1 실측):

```
chat.json = [배치, 배치, 배치]
배치 = { batch_number, turns, time_anchor }
turns = [[msg, msg], [msg, msg, msg, msg], ...]
msg   = { role, id, content, time_anchor?, index?, question_type? }
```

`time_anchor`가 두 군데에 있어 헷갈리는데, **배치 레벨은 항상 비어 있음.** 실제 날짜는
배치의 **맨 첫 user 메시지 하나**에만 붙음 (`question_type: main_question`, `index: "1,1"`).
100K_1이면 이럼.

| | 메시지 | 배치 `time_anchor` | 메시지에 붙은 anchor |
|---|---|---|---|
| 배치 1 | 60 | `None` | 1개 · `March-15-2024` |
| 배치 2 | 56 | `None` | 1개 · `April-05-2024` |
| 배치 3 | 72 | `None` | 1개 · `April-25-2024` |

**100K 20개 대화 전수로 확인한 불변식** (대화마다 배치 수는 다름):

- 배치마다 `time_anchor`가 **정확히 1개** (20/20)
- 배치 레벨 `time_anchor`는 **항상 비어 있음** (20/20)
- 따라서 **고유 날짜 수 = 배치 수**

| 배치 수 | 대화 |
|---|---|
| 3개 | 5개 (대화 1~5) |
| 5개 | 15개 (대화 6~20) |

메시지 수는 188~392개로 두 배 넘게 벌어짐. 즉 **메시지 60~80개당 날짜 하나**꼴이고,
나머지 메시지에는 시각 정보가 없음. HaluMem이 세션마다 `start_time`을 주던 것과 근본적으로
다름. 500K·1M은 로컬 sparse checkout에 없어 미확인이며 서버에서 같은 스크립트로 재확인할 것.

⚠ 10M은 구조가 한 겹 더 깊음. 원본 `create_chunking`에 `for plan in messages:
for batch in list(plan.values())[0]` 분기가 따로 있음. 10M을 돌리려면 `parse_chat`부터
손봐야 함.

그래서 `temporal_reasoning` 문항(정답이 "3월 3일부터 4월 15일까지 43일" 같은 형태)이
풀리려면 **대화 본문에 텍스트로 적힌 날짜**가 메모리에 남아야 함. 배치 앵커로는 안 됨.
BEAM 데이터는 본문에 날짜가 자주 나오는 편임 (첫 메시지가 "Time Anchor of March 15, 2024"
라고 말하고, 이후에도 "completed sprint 1 on March 29" 식으로 등장).

또 하나. turn 길이가 **전부 짝수**임 (100K 5개 대화의 turn 538개 기준 길이 2가 352개,
4가 99개, 6이 87개, 홀수 0개). 이 사실이 §2-2의 청킹 판단에 쓰임.

### 2-2. 투입 단위: 공식과 mem0 하네스가 같은 값이라 고민할 것이 없었음

BEAM 원본의 `create_chunking()`(`src/answer_probing_questions/long_term_memory_methods.py`)이
네 가지를 제공함: `pair_chunk`(turn 안에서 2메시지씩) · `turn_chunk`(turn 통째로) ·
`kv`(LLM episodic memory) · `light`(LightMem + scratchpad).

그리고 **README가 권장하는 기본 RAG 설정이 `pair_chunk`임**:

> Set `EVAL_TYPE="rag"`, `RETRIEVAL_METHOD="pair_chunk"` and `RETRIEVER="dense"`

mem0 하네스도 2메시지 청크임. **양쪽이 같은 값이라 선택의 여지가 없었음.** 이 항목은
"mem0를 따른 이탈"이 아니라 두 출처가 합치한 지점임.

구현이 미세하게 다른데 결과는 동일함. BEAM은 turn 안에서 짝을 짓고(`turn[i:i+2]`), 우리는
배치의 메시지를 평평하게 편 뒤 짝을 지음(`clean[i:i+2]`). turn 길이가 홀수면 갈리는데
§2-1에서 확인했듯 홀수 turn이 하나도 없어서 두 방식이 같은 짝을 만듦.

### 2-3. 시간 정보가 어디서 어떻게 쓰이나

날짜가 배치당 하나뿐이므로 **배치의 첫 앵커를 그 배치의 모든 청크에** 부여함.

```python
anchor = next((m["time_anchor"] for m in msgs if m.get("time_anchor")), None)
add_with_retry(memory, chunk, user_id=user_id,
               metadata={"session_time": anchor or "unknown_time", "batch": bi})
```

100K_1이면 94개 청크가 세 날짜로 나뉨 (배치 0 → March-15, 1 → April-05, 2 → April-25).

**① 추출 단계: 날짜를 안 봄.** mem0 `_add_to_vector_store`는 메시지만 프롬프트에 넣고
`metadata`는 벡터 payload에만 붙임.

```python
parsed_messages = parse_messages(messages)
system_prompt, user_prompt = get_fact_retrieval_messages(parsed_messages)   # metadata 없음
...
metadata=deepcopy(metadata),   # 저장할 때만
```

즉 "2024년 3월 15일에 X를 했다" 같은 메모리가 생기려면 그 날짜가 **대화 본문에** 있어야 함.

**② 검색 단계: 날짜를 안 씀.** 필터 없이 코사인 유사도만 씀. `session_time`은 결과에
딸려 나올 뿐임. 100K_1 검색 결과 195건 전부 `session_time`이 채워져 있고 값은 세 종류임.
HaluMem에서 확인한 **검색 계층의 시간 인지 부재**가 여기서도 그대로임.

**③ 답변 생성 단계: 여기서만 씀.** `build_context`가 cutoff로 자른 뒤 시간순 오름차순으로
정렬하고 줄마다 `[날짜]` 접두사를 붙임.

```
1. [March-15-2024] Has a simple transaction input form and wants to improve its UX
2. [April-05-2024] Completed sprint 1 on March 29
```

⚠ **자르기가 정렬보다 먼저임.** 순서를 바꾸면 상위 N개 대신 "오래된 것 N개"를 주게 되어
검색 랭킹이 무의미해짐.

⚠ **정렬이 문자열 기준이라 `April-05-2024 < March-15-2024`로 잘못 정렬됨.** 날짜가 배치당
하나뿐이라 같은 값끼리 뭉치는 그룹핑 효과는 유지되지만 시간순은 정확하지 않음. 고칠 지점임.

**공식 RAG 기준선과 비교하면 우리 쪽이 시간 정보에서 유리함.** 원본 `handling_context()`는
검색 순서 그대로 이어붙이고 29,000토큰에서 자르며, 메타데이터가
`{batch_number, turn_number, pair_number}`뿐이라 **날짜가 프롬프트에 아예 안 들어감.**

| | BEAM 원본 RAG | 우리 |
|---|---|---|
| 청크 단위 | 2메시지 (`pair_chunk`) | 2메시지 |
| 청크 중복 | **turn 길이만큼 중복** (§2-5) | 없음 |
| 저장 | 원문 그대로 | mem0가 사실 추출 |
| 검색 | dense top-k | dense top-200 |
| 컨텍스트 순서 | 검색 점수 순 | **시간순 오름차순** |
| 날짜 표기 | **없음** | **`[날짜]` 접두사** |
| 예산 | 29,000토큰 | cutoff 20/50/100/200개 |

저장 방식과 예산 단위까지 다르므로 **공식 기준선 수치와 직접 비교하지 않음.** 우리 실험은
mem0 레인 안에서의 상대 비교로만 읽음.

### 2-4. 프로토콜 선택 표

| 항목 | 값 | 근거 |
|---|---|---|
| 투입 단위 | 2메시지 청크 | BEAM 공식 = mem0 하네스 (§2-2) |
| 시각 부여 | 배치의 첫 `time_anchor`를 그 배치 전 청크에 | 날짜가 배치당 하나뿐 (§2-3) |
| 컨텍스트 포맷 | 시간순 정렬 + `[날짜]` 접두사 | mem0 하네스 |
| 검색 | top-200 한 번, cutoff 20/50/100/200으로 자름 | BEAM 기준 세팅 |
| judge 프롬프트 | 논문 원본 무수정 import | 무수정 원칙 |
| 답변 생성 프롬프트 | mem0 하네스 이식 (공식본도 함께 측정) | §7-6 |
| agent / generator / judge | gpt-oss-120b (agent medium, 나머지 high) | 기존 그리드와 통제 일치 |

top-k를 HaluMem의 20 대신 BEAM 기준인 200으로 잡았음. 20이라는 숫자 자체에는 근거가 없기
때문임. HaluMem에서 20을 쓴 근거는 "HaluMem의 기준 세팅"이었으므로, 같은 원칙을 적용하면
BEAM에서는 200이 나옴.

두 출처를 섞은 것처럼 보이지만 가르는 규칙은 하나임. **BEAM에 원본이 있으면 BEAM을 따르고,
없으면 mem0 하네스를 따름.**

BEAM은 메모리 시스템을 평가 대상으로 두지 않음. RAG 기준선은 있지만 **원문 청크를 그대로
색인**할 뿐이라, "무엇을 사실로 뽑아 어떻게 저장하고 갱신할지"에 대한 원본이 없음. 시각을
어떻게 부여할지, 컨텍스트를 몇 개로 끊을지도 마찬가지임. 이 항목들은 mem0 하네스를 따랐음.

단, **투입 단위는 예외적으로 양쪽에 원본이 있고 값이 같음** (둘 다 2메시지). §2-2 참조.

반면 답변 생성과 채점은 BEAM에 원본이 있음. 채점은 원본을 그대로 씀. 답변 생성은 이 규칙의
유일한 예외로 mem0 이식본을 대표값에 씀. 공식 답변 프롬프트가 공식 rubric과 서로 어긋나 있고,
mem0 팀 발표 수치와 비교하려면 그쪽에 맞춰야 하기 때문임. 공식본도 같이 돌려서 나란히 보고함.
근거와 실측은 §7에 있음.

### 2-5. 공식 코드와 다르게 한 곳 두 군데

**judge 프롬프트의 `<question>` 치환자를 채움.** 공식 `compute_metrics.py`는 이 자리를 비운 채
호출함. 프롬프트 본문에 "질문에 응답하지 않으면 0점을 주고 중단하라"는 규칙이 있는데,
질문이 비면 그 규칙이 작동하지 않음. 우리는 채워서 호출함.

**`event_ordering_score` 계열 함수를 import 대신 복사함.** `compute_metrics.py`가 맨 위에서
`from src.llm import *`를 하는데 `src/llm.py`가 import 시점에 OpenAI 클라이언트 세 개를 생성함.
키가 없으면 그 자리에서 죽고 `sentence_transformers`·`rouge_score`·`nltk`도 함께 끌려옴.
`src/beam/beam_official.py`에 원본 그대로 옮기고 출처 커밋과 줄번호를 주석에 박아둠.

### 2-6. 공식 RAG 기준선 코드에 청크 중복 버그가 있음

우리가 쓰지 않는 코드지만, **공식 기준선 수치를 그대로 믿기 어려운 근거**라 기록해둠.
`create_chunking()`의 `pair_chunk` 분기임.

```python
for turn_number, turn in enumerate(turns):
    for message in turn:                                     # ← 이 루프가
        pairs = [turn[i:i+2] for i in range(0, len(turn), 2)]
        for pair_number, pair in enumerate(pairs):
            chunks.append({...})                             # ← 여기를 감싸고 있음
```

`pairs`가 `message`와 무관한데 `for message in turn` 안에 있음. **같은 청크가 turn 길이만큼
중복 추가됨.** 메타데이터(`batch_number`/`turn_number`/`pair_number`)까지 같아서 완전한 중복임.

| turn 길이 | 나와야 할 청크 | 실제 생성 | 배수 |
|---|---|---|---|
| 2 | 1 | 2 | 2배 |
| 4 | 2 | 8 | 4배 |
| 6 | 3 | 18 | 6배 |

검색 코퍼스가 중복으로 부풀면 top-k에 같은 내용이 여러 번 올라와 다양성이 죽음. 10M 분기도
같은 구조임. 그리고 10M 분기에는 `len(pair) == 2` 가드가 있는데 일반 분기에는 없어서 홀수
길이 turn이 들어오면 `pair[1]`에서 IndexError가 남 (실제 데이터는 전부 짝수라 안 터짐).

§6-3의 `extract_facts` 덮어쓰기 버그와 같은 계열임. **공식 코드의 서술과 동작이 어긋나는
지점이 지금까지 셋임** (judge 프롬프트의 빈 `<question>`, `event_ordering`의 사실 분할 폐기,
이 청크 중복).

## 3. 파이프라인 실측 (100K 버킷)

대화 20개, 청크 2,866개, 문항 400개.

### 3-1. 처리량

| 워커 | 청크당 지연 | 처리량 | 1워커 대비 |
|---|---|---|---|
| 1 | 5.41초 | 0.185 청크/초 | 1.0배 |
| 4 | 7.52초 | 0.532 | 2.9배 |
| 20 | 21.31초 | 0.939 | **5.1배** |

20워커에서 이미 포화에 가까움. 워커를 4배 늘렸는데 처리량은 1.8배만 늘었음. 벽시계는
가장 긴 대화(196청크)가 결정하므로 약 70분이었음.

단계별로는 투입 70분, 답변 48분, 채점 72분임.

### 3-2. 저장 메모리

저장 개수가 **100~407개, 중앙값 278개**임. 주제에 따라 밀도가 2배 이상 갈림.

| 주제 | 청크당 저장 메모리 |
|---|---|
| Math | 0.90 ~ 0.94 |
| Coding | 1.25 ~ 2.07 |
| Writing, Philosophy, Lifestyle, Therapy, Legal | 1.8 ~ 2.2 |

Math가 가장 적음. 수식과 계산 위주라 추출할 사실이 적었던 것으로 보임. 능력별 점수를 읽을 때

### 3-3. 회차 간 흔들림

대화 1번을 세 번 투입했는데 저장 개수가 **168 / 186 / 195**로 나옴. 같은 입력인데 16% 벌어짐.
추출과 갱신 결정이 LLM 호출이라 회차마다 다른 판단을 내림. HaluMem에서 잰 노이즈 바닥과

## 5. 판독

### 5-1. 평균만 보면 아무 일도 안 일어난 것처럼 보임

전체 평균은 0.493 → 0.539 → 0.540 → 0.531로, 50에서 꺾인 뒤 평평함. 여기까지만 보면

**그 평균은 반대 방향 둘이 상쇄된 결과임.**

컨텍스트를 늘릴수록 오르는 쪽은 `summarization`(+0.267), `temporal_reasoning`(+0.138),
`event_ordering`(+0.071)임. 전체를 훑어야 답이 나오는 작업들임. summarization은 두 배 넘게 오름.

떨어지는 쪽은 `abstention`(−0.100), `preference_following`(−0.037), `instruction_following`(−0.025)임.

섞여 들어가면 흔들림.

**단일 점수로 메모리 시스템을 평가하면 이 구조가 통째로 사라짐.** 능력별로 나눠 봐야 하는
이유가 실측으로 나온 셈임.

### 5-2. 검색 예산의 이득이 50에서 멈춤 (⚠ 500K에서 뒤집힘)

100K에서는 top-50 이후로 이득이 없음. mem0가 1M에서 top-200과 top-50을 비교해 −3.7p를
보고한 것과 방향이 다름. 저장소 크기 차이로 보임. 100K는 저장소가 100~407개라 50개만
뽑아도 상당 부분을 덮지만, 1M은 훨씬 크므로 200이 유리해질 것으로 예상함.

> **⚠ 정정 (2026-08-18, 500K 12대화 기준).** 위 가설이 맞았고, 따라서 **"50에서 멈춘다"는
> 100K 한정 현상임.** 저장소가 커지면 200까지 단조로 오름.
>
> | 구간 | 100K (20대화) | 500K (12대화) |
> |---|---|---|
> | 20 → 50 | +0.046 | +0.016 |
> | 50 → 100 | +0.001 | +0.016 |
> | 100 → 200 | **−0.009** | **+0.014** |
>
> 100K는 top-200이 저장소를 넘는 문항이 400개 중 **100개**이고 500K는 **0/240**임 (§3-4).
> 100K의 top-100과 top-200은 상당 부분 같은 것을 다시 준 것이라 희석이 −0.009로 나타남.
> **검색 예산 비교는 저장소가 예산보다 클 때만 의미가 있음.**
>
> ⚠ 단, 이 곡선은 **답변 생성 프롬프트에 종속됨.** 같은 500K 저장소인데 BEAM 공식
> 프롬프트로 답하면 0.371 → 0.440 → 0.428 → 0.426으로 50에서 꺾임. 짧게 답하라고
> 시키면 컨텍스트를 더 줘도 쓰지 못함. **검색 예산의 효과를 논하려면 답변 규약을
> 먼저 고정해야 함** (§7).
>
> ⚠ 500K 12대화는 Qdrant 사망(§8) 전에 먼저 끝난 것들이라 작은 대화 쪽으로 치우쳐 있음
> (완료분 평균 약 508청크 대 남은 23개 약 559청크). 35대화가 다 모이기 전에는 버킷 간
> **절대 점수 비교를 하지 않음.** 여기서 읽는 것은 곡선의 모양뿐임.

## 6. event_ordering: 공식 지표에 결함이 있음

같은 응답에 대해 세 지표가 전혀 다른 값을 냄.

```
nugget 평균 (mem0 하네스)        0.374
tau_norm    (공식 리포트)        0.239
final_score (tau_norm × f1)      0.052
```

### 6-1. 각각이 재는 것

**nugget 평균.** judge가 rubric 항목마다 "응답이 이 기준을 만족하는가"를 0/0.5/1로 매긴 값의
평균임. rubric 항목은 `Core functionality` 같은 사건 이름임. **순서 개념이 아예 없음.**
사건 세 개를 거꾸로 나열해도 세 개를 다 언급했으면 만점임.

**tau_norm.** 정답 사건 순서와 응답 속 순서 사이의 Kendall tau-b를 [0,1]로 옮긴 값임. 순서는
보지만, 언급되지 않은 사건이 전부 같은 순위(`tie_rank`)로 뒤에 몰리고 그게 "순서가 맞다"로
계산됨. 원본 스코어러를 그대로 옮겨 시나리오를 넣어보면 이렇게 나옴.

| 응답 | F1 | tau_norm | final |
|---|---|---|---|
| 3줄로 정확한 순서 | 1.000 | 1.000 | 1.000 |
| 3개 다 맞췄는데 순서 완전 역순 | 1.000 | **0.000** | 0.000 |
| 한 문단에 3개 다 언급 | 0.500 | 0.908 | 0.454 |
| 한 문단에 **1개만** 언급 | 0.500 | **0.908** | 0.454 |
| "정보가 부족합니다" | 0.000 | 0.146 | 0.000 |

**적게 말할수록 유리함.** 사건 하나만 언급한 답변(0.908)이 세 개를 다 맞췄지만 순서가 틀린
답변(0.000)보다 높음. 아무것도 못 맞혀도 0.146이 나와 바닥이 막혀 있음.

**final_score.** 순서와 회수율을 둘 다 보는 유일한 값인데, 실측에서 **절반이 0**임.

| 지표 | 평균 | 0인 건 |
|---|---|---|
| precision | 0.139 | 80/160 |
| recall | 0.154 | 80/160 |
| f1 | 0.142 | 80/160 |
| tau_norm | 0.239 | **0/160** |
| final_score | 0.052 | 80/160 |

### 6-2. f1이 무너지는 이유

응답 줄과 rubric 항목을 맞춰주는 것이 LLM 동등성 판정기(`llm_equivalence`)인데, 이것이
실패함. 실제 사례임.

```
rubric : ['Core functionality', 'Transaction error handling', 'Security and deployment']
응답   : 1. User Authentication (registration & login) – first mentioned March 15 2024
         2. Expense-classification improvement – first mentioned April 5 2024
         3. Pragmatic Security Enhancements ...
nugget : [1.0, 0.0, 0.5] → 0.5점
f1     : 0.0 → final_score 0.0
```

같은 응답에 두 채점기가 **0.5와 0.0**을 매김. 던지는 질문이 다르기 때문임.

- nugget judge: "이 응답이 `Core functionality` 기준을 만족하는가" → 프롬프트에 의미 기반
  판단 조항이 있어 `User Authentication (registration & login)`을 인정하고 1.0을 줌
- `llm_equivalence`: "이 두 조각이 **같은 사건**을 서술하는가" → 2단어짜리 라벨과 날짜까지
  붙은 한 줄을 비교하니 NO. 세 개 다 NO면 매칭 0개, f1 0, final_score 0

응답이 길고 장식이 많은 것도 매칭 실패에 한몫했을 것이라 의심했으나 **실측으로 기각됨.**
공식 프롬프트로 답변을 짧게 만든 뒤 f1이 0.142에서 0.112로 오히려 떨어졌고, f1이 0인 문항은
80건에서 94건으로 늘었음. 짧아지면 동등성 판정이 붙을 것이라는 예상이 틀렸음. 응답이 짧으면
줄 수가 rubric 항목 수보다 적어져서 재현율 쪽이 무너짐. **매칭 실패는 응답 길이와 무관한
채점기 결함이 맞음.** `tau_norm`의 `tie_rank` 결함(§6-1)도 그대로 남음.

### 6-3. 원본 코드의 또 다른 문제

`evaluate_event_ordering`이 `extract_facts`로 응답을 사실 단위로 쪼갠 뒤, 바로 다음 줄에서
`llm_response.split("\n")`으로 덮어씀. LLM 사실 분할 결과가 버려지고 개행 분리로 동작함.
논문 서술("LLM equivalence detector로 정렬")과 실제 코드가 어긋남. 재현할 때 서술 대신 코드를 따라야 한다는
근거임.

### 6-4. 어느 값을 쓸 것인가

셋 다 결함이 있고, **nugget 평균이 그중 제일 덜 나쁨.**

- `final_score`: 매칭 실패로 절반이 0. 쓸 수 없음
- `tau_norm`: 바닥이 막혀 변별력이 없고 적게 말할수록 유리. 게다가 혼자만 다른 계열이라
  나머지 9개 능력과 한 표에 놓으면 오독을 부름
- `nugget 평균`: 순서를 안 보는 문제가 있지만, 나머지 능력과 척도가 같아 비교 가능함

**대표값으로 nugget 평균을 쓰고 `tau_norm`을 병기함.** 공식 리포트가 최종 점수로 쓰는 것이
하필 `tau_norm`이므로, 공식 수치를 인용할 때는 이 차이를 반드시 밝혀야 함.

## 7. 답변 생성 프롬프트가 점수를 흔듦

100K 초기 실행에서 답변이 눈에 띄게 장황했음. 원인을 되짚으니 모델 특성이 아니라 프롬프트
선택이었고, 저장·검색을 하나도 안 건드린 채 점수가 움직이는 변인이었음.

### 7-1. 두 프롬프트가 서로 다른 것을 시킴

| | BEAM 공식 (`answer_generation_for_rag`) | mem0 하네스 이식본 |
|---|---|---|
| 분량 | 378자 | 약 1,200자, 규칙 9개 |
| 길이 지시 | "간결하게", "설명 없이 답만 출력" | 없음 |
| 세부 지시 | 없음 | "이름·날짜·숫자를 정확히 담아라" |
| 근거 없음 처리 | 지시 없음 | 정확한 문장을 지정해 줌 |
| 순서 질문 | 지시 없음 | "시간순으로 제시하라" |

두 프롬프트가 길이에 대해 정반대를 시킴. 공식은 설명을 붙이지 말라고 하고, 이식본은 세부를
빠짐없이 담으라고 하면서 상한을 안 줌. 후자로 돌린 결과가 아래임.

### 7-2. 실측 (100K, mem0 이식본)

- 답변 길이 중앙값 **669자**, 최대 **18,903자**. rubric 항목이 1개뿐인 문항에 12,542자를 쓴
  사례가 있었음
- 길이와 점수의 Spearman ρ가 능력마다 부호까지 갈림: `abstention` **−0.869**,
  `summarization` **+0.467**, `information_extraction` −0.277
- rubric 1개짜리 문항은 −0.195, rubric 2개 이상은 최대 +0.445. 항목이 많으면 길게 쓸수록
  하나쯤 걸리고, 항목이 하나면 길게 쓸수록 초점이 흐려짐
- cutoff가 커질수록 답변이 길어짐 (top-20 587자 → top-200 802자)

마지막 항목이 제일 곤란함. cutoff 곡선은 검색 예산의 효과를 보려고 그린 것인데, cutoff를
올리면 답변 길이도 같이 올라가서 두 효과가 섞임. §5-2의 "50에서 이득이 멈춤"이 검색의 성질인지
길이의 성질인지 이 상태로는 못 가름.

### 7-3. 바꾼 뒤 실측: 길이

같은 투입·같은 검색 결과 위에서 답변 생성만 다시 돌린 결과임 (1,600건).

| | mem0 이식본 | BEAM 공식 |
|---|---|---|
| 길이 중앙값 | 669자 | **76자** |
| 길이 평균 | – | 306자 |
| 길이 최대 | 18,903자 | 6,283자 |
| 빈 답변 | 193건 (예산 4096) | **2건** (예산 32768) |

중앙값이 8.8배 줄었음. 프롬프트 한 줄("설명 없이 답만 출력")이 한 일임.

**빈 답변이 거의 사라진 것도 같은 원인임.** reasoning 모델은 사고 토큰과 출력 토큰이
`max_completion_tokens` 하나를 나눠 씀. 출력이 짧아지니 사고에 쓸 여유가 생겼음. §8에
기록한 "예산을 4096에서 32768로 올려 해결" 은 증상을 덮은 것이었고, 원인의 절반은
답변을 길게 쓰라고 시킨 프롬프트였음. 남은 2건은 둘 다 `multi_session_reasoning`의
top-200이고 `finish_reason`이 `length`임.

**그 2건은 메꾸지 않고 0점으로 두었음.** 능력당 문항이 40개라 그 칸에서만 5%가 강제
0점이 되고 약 −0.025 눌림. 전체 1,600건 기준으로는 0.125%라 평균과 능력별 순위는
바뀌지 않음. `multi_session_reasoning`의 top-200 칸 하나만 읽을 때 이 값을 감안할 것.

mem0 이식본에서 능력별 길이 중앙값이 40배까지 벌어져 있었던 것도 같이 기록해둠.
`preference_following` 6,344자 · `summarization` 5,762자 · `instruction_following` 4,430자
대 `knowledge_update` 155자 · `temporal_reasoning` 226자. 길이 상관의 부호가 능력마다
갈렸던 이유가 여기에 있음.

### 7-4. 점수: 공식 프롬프트가 전면적으로 낮음

문항 단위로 짝지어 대응표본 Wilcoxon으로 봤음 (1,600쌍, `src/beam/compare_prompts.py`).

| | top-20 | top-50 | top-100 | top-200 |
|---|---|---|---|---|
| mem0 이식본 | 0.493 | 0.539 | 0.540 | 0.531 |
| BEAM 공식 | 0.385 | 0.404 | 0.413 | 0.416 |
| 차이 | −0.108\*\*\* | −0.135\*\*\* | −0.127\*\*\* | −0.115\*\*\* |

10개 능력 중 8개가 유의하게 떨어졌음. 오른 것은 `knowledge_update`(+0.009, 유의하지 않음)
하나뿐임. 문항 단위로는 오름 186 · 내림 590 · 동일 824임.

`abstention`이 어느 쪽으로 갈지 모르겠다고 §7-3에 적었는데, 답은 **거의 안 움직임**이었음
(−0.019, 유의하지 않음). 길이가 5.4배 짧아졌는데도 그럼. 길이 상관 −0.869은 인과가 아니었음.

**500K에서 재현됨** (12대화 240문항, §5-2의 표본 주의 그대로 적용).

100K의 −0.108~−0.135와 방향도 크기도 같음. 버킷 하나의 우연이 아님.

### 7-5. 왜: rubric이 서술형 답변을 전제함

`contradiction_resolution`의 rubric 4항목이 전부 "~을 언급하라"임.

```
1. 모순된 정보가 있다고 말할 것
2. "Flask 라우트를 쓴 적 없다"고 했던 것을 언급할 것
3. "홈페이지 라우트를 구현했다"고도 했던 것을 언급할 것
4. 어느 쪽이 맞는지 말할 것
```

공식 프롬프트는 `Only output the answer to the question without any explanation`이라고 시킴.
모델은 시킨 대로 `No`(3자)라고 답했고 4항목 중 0개를 맞았음. **BEAM 공식 답변 프롬프트가
BEAM 공식 rubric과 서로 어긋나 있음.**

짧은 답으로 채울 수 있는 rubric 항목은 "답 그 자체" 하나뿐임. 나머지 언급요구 항목은
원리적으로 못 채움. 그 비율이 하락폭을 설명함.

| 능력 | 언급요구 항목 | 못 채우는 비율 | 실측 차이 |
|---|---|---|---|
| contradiction_resolution | 4.00 | 0.750 | −0.434 |
| multi_session_reasoning | 2.50 | 0.600 | −0.109 |
| information_extraction | 2.30 | 0.565 | −0.124 |
| temporal_reasoning | 1.88 | 0.467 | −0.117 |
| knowledge_update | 1.05 | 0.048 | +0.009 |
| summarization | 0.12 | 0 | −0.022 |
| event_ordering | 0.03 | 0 | −0.050 |
| abstention | 0.03 | 0 | −0.019 |

Spearman ρ = −0.511이지만 n=10이라 p=0.13임. 상관보다 rubric 원문이 직접 증거임.
`event_ordering`은 rubric 항목이 5.33개로 제일 많은데도 −0.050뿐임. 그 rubric들이
"언급하라" 형식이 아니기 때문임. 항목 수로는 설명이 안 되고 **형식**이 정함.

**결정적인 사례** (`temporal_reasoning`, 100K_10 idx0):

| | 답변 | rubric 1 (43일) | rubric 2 (3월 3일~4월 15일) | 점수 |
|---|---|---|---|---|
| mem0 이식본 | "53일" (계산 틀림) | 0.0 | 0.0 | **0.0** |
| BEAM 공식 | "43" (계산 맞음) | 1.0 | 0.0 | **0.5** |

공식 쪽이 추론을 더 잘하고도 0.5에 막혔음. 날짜 범위를 말 안 했기 때문임.
**짧은 프롬프트가 추론을 망가뜨린 것이 아님. 보고를 줄였고, rubric은 보고를 채점함.**
§7-2에서 길이와 점수의 상관으로 관찰했던 것의 기전이 이것임.

예외가 둘 있음. `instruction_following`(−0.250)과 `preference_following`(−0.096)은 언급요구
항목이 거의 없는데 크게 떨어졌음. 이 둘은 mem0 이식본에서 답변이 제일 길었던 능력임
(4,430자, 6,344자). **벤치마크가 재려는 지시 준수를 답변 프롬프트가 위에서 덮어쓴 것**으로
보이는데, rubric 원문을 더 봐야 확정됨.

### 7-6. 대표값은 mem0 이식본으로 함

근거 둘임.

1. mem0 팀이 발표한 BEAM 수치가 그들 프롬프트로 나온 것임. 비교하려면 맞춰야 함
2. rubric이 요구하는 답변 형식이 서술형임. 공식 답변 프롬프트는 거기에 안 맞음

점수가 높아서 고르는 것이 아님을 분명히 해둠. 둘 다 보고하고 대시보드에서 나란히 봄.

그리고 **이 간극 자체가 결과임.** 같은 저장소, 같은 검색 결과에서 0.531과 0.416이 나옴.
상대 25% 차이임. **BEAM 수치를 인용할 때 답변 생성 프롬프트를 밝히지 않으면 해석이
불가능함.** 메모리 시스템의 성능이라고 부르는 값의 4분의 1이 답변 규약의 몫임.

## 8. 실행 중 밟은 함정

기록해두지 않으면 반복할 것들임.

**답변 생성에서 12%가 빈 문자열로 나옴.** reasoning 모델은 `max_completion_tokens`에 사고 토큰이
포함됨. 4096으로 두니 1,600건 중 193건에서 사고에 예산을 다 쓰고 `content`가 비었음. 분포가
원인을 그대로 보여줌: cutoff가 클수록 단조 증가(top-20 5.2% → top-200 18.8%), 추론이 무거운
능력에 몰림(`event_ordering` 45, `multi_session_reasoning` 42 대 `abstention` 4). 32768로 올려
192건이 살아나고 1건은 65536이 필요했음. `finish_reason`을 기록하도록 고침.

**채점 결과를 맨 끝에 한 번만 저장하는 구조였음.** 5,500콜 1.5시간치가 출력 디렉토리 문제로
통째로 유실됨. 대화 하나가 끝날 때마다 저장하도록 고쳤음. 오래 걸리는 작업은 단위마다 저장하고
중단 후 이어서 돌 수 있어야 함.

**`.gitignore`의 `BEAM/`이 `eval/mem0-classic-oss/beam/`까지 무시했음.** macOS는
`core.ignorecase=true`라 대소문자를 무시함. 루트 고정이 필요하면 `/BEAM/`로 써야 함.

**Qdrant가 죽어 500K 23대화와 1M 35대화를 통째로 날렸음.** 2026-08-18 07:57:03에
`failed to allocate an alternative stack: Cannot allocate memory (os error 12)`로 프로세스가
죽었음. 시스템 메모리는 481Gi가 남아 있었으므로 RAM 문제가 아님. **투입 스크립트가 대화마다
컬렉션을 만들고 끝나도 안 지운 것이 원인임.** 컬렉션이 180개까지 쌓였고(HaluMem 122 + BEAM 57)
컬렉션마다 붙는 스레드가 한계를 넘겼음. 그때 돌던 23개가 2분 안에 전부 실패했고, 1시간 반 뒤
시작한 1M 투입 35개는 Qdrant가 계속 죽어 있어 즉시 전멸했음.

대가가 컸던 이유는 **아무도 죽은 줄 몰랐다는 것**임. 실패는 `tmp/*_error.log`에만 남고
스크립트는 정상 종료함. 4시간 반이 지나서야 발견했음. 셋 다 고쳤음.

- `ingest_beam.py`가 대화가 끝나면 그 컬렉션을 지움. 동시 존재량이 워커 수를 안 넘음
- Qdrant 생존을 1분마다 확인해 로그에 남기는 감시 세션을 띄움
- `vm.max_map_count`를 65530에서 262144로 올림 (원인으로 확정된 것은 아니고 예방 차원임)

**장시간 작업은 실패를 소리 내야 함.** 성공한 것만 세지 말고 실패 개수를 최종 요약에 찍고,
의존하는 외부 서비스는 따로 감시할 것.
