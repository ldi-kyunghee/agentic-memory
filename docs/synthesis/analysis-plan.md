# 종합 분석 계획: 수치에서 문제 정의로

작성 2026-08-29. LIGHT 전 벤치마크 완주 후 실행할 분석의 설계도임.

## 1. 목적

지금까지 쌓인 것은 "벤치 X의 지표 Y에서 시스템 Z가 몇 점"이라는 표면 수치임.
이 분석의 산출물은 점수표를 넘어선 것, 즉 **현존 메모리 벤치마크와 메모리
시스템의 한계·맹점에 대한 problem statement 와 research question**임.

원칙 두 가지.

- **수치와 사례를 항상 짝으로 읽음.** 집계 수치에서 이상한 점을 찾고, 그것을
  만든 실제 문항·검색 결과·답변·판정을 눈으로 확인한 뒤에만 문제로 승격함.
  사례 없는 문제 정의는 금지.
- **여러 개가 나와도 됨.** 하나의 큰 결론을 조립하려고 무리하지 않음. 카드
  단위로 독립적으로 성립하는 문제를 여러 장 만들고, 마지막에 관계를 정리함.

## 2. 이 분석에서 하지 않는 것

- **새 실험을 돌리지 않음.** 입력은 이미 끝난 산출물(judge 파일·ingest 결과·
  trace·비용 계측)뿐이고 GPU 를 쓰지 않음. §6에 적힌 "확인할 것"들은 전부
  기존 파일을 다시 읽는 계산임. 예를 들어 과제 구성비 재가중은 이미 있는
  문항별 점수의 산수이고, 정확도 대비 비용도 이미 있는 계측 파일의 산수임.
- 분석 중에 새 실험이 필요하다는 판단이 서면, 그 필요성 자체를 보고하고 멈춤.
  임의로 실험을 늘리지 않음.

## 3. 산출물 형식: 문제 카드

카드 한 장 = 문제 하나. 필수 필드:

| 필드 | 내용 |
|---|---|
| 현상 | 무엇이 이상한가 (한 문장) |
| 수치 근거 | 우리 산출물에서 재확인한 수치 (경로 포함) |
| 사례 근거 | 실제 문항 2~5건 (문항 키 포함, 재현 가능) |
| 반례 검토 | 이 현상을 평범하게 설명하는 가설들과 그 기각 근거 |
| 문헌 연결 | 문헌조사 RQ 7건 · 저장소 가설 리포트의 다섯 난제와의 관계 |
| Problem statement | 벤치마크의 맹점인지, 시스템의 한계인지, 둘 다인지 명시 |
| 연구 질문 | 분야 수준의 질문 (§4 기준) |
| 질문이 요구하는 것 | 새 벤치마크 설계인지, 새 측정 방법인지, 새 시스템 부류인지 |

최종 문서는 `docs/synthesis/problem-cards.md` (카드 모음) +
`docs/synthesis/synthesis.md` (카드 간 관계와 종합)로 나눔.

## 4. 연구 질문의 기준

지난 초안의 실패: 연구 질문을 "지금 세팅에서 바로 검증 가능한 것"으로만
적어서, 추가 실험 계획 수준의 좁은 질문이 나왔음. 고친 기준:

- **근거와 질문의 역할을 나눔.** 우리 수치·사례는 문제가 실재한다는 증거로만
  씀. 연구 질문은 그 증거에서 출발하되, 우리 세팅으로 검증 가능한지와
  무관하게 분야 수준에서 던짐.
- **좋은 질문은 전제를 의심함.** "지표를 하나 더 재면 어떻게 되는가"는 나쁜
  질문임. "그 지표가 재고 있다고 주장하는 것을 실제로 재는가", "이 비교
  관행이 애초에 성립하는가"가 좋은 질문임.
- 질문마다 그것이 요구하는 새로운 것(벤치마크 설계, 측정 방법, 시스템 부류)을
  명시함. 그래야 질문이 연구 프로그램으로 이어짐.

## 5. 증거 목록

3 시스템(mem0 classic 0.1.118 · mem0 v3 2.0.18 · LIGHT) × 3 벤치마크. 전부
같은 조건(agent gpt-oss-120b medium · 답변/채점 gpt-oss-120b high ·
Qwen3-Embedding-4B)에서 돌았음.

| 벤치마크 | 세팅 | 문항 단위 판정 | 경로 기준 |
|---|---|---|---|
| HaluMem | 20유저 (QA 3,467 · 평가 기준 18,415) | QA result_type + memory 4종 레코드 | `runs.yaml` halumem.scales.20u.by_system |
| BEAM | 100K·500K, BEAM 공식 프롬프트 | 문항×cutoff 4벌 score(0~1) + nugget | beam.buckets.{100k,500k}-beamprompt |
| Memora | weekly·monthly | 문항 FAMA/MPA + criteria 단위 판정 | memora.periods.{weekly,monthly} |

수치 밖 증거:

- **trace**: 전 시스템·전 투입의 LLM(입력·출력 토큰)·임베딩·검색 호출 원문.
  검색이 무엇을 올렸는지, 추출이 무엇을 버렸는지 문항 단위로 복원 가능.
- **비용 계측**: `cost/{bench}-{setting}-{system}/` 단계별(투입·질의·답변·채점)
  호출 수·입력·출력·컨텍스트 분포.
- **재현성 실측**: 투입 반복 편차(전체 ±0.17%, 대화 단위 최대 11.1%),
  QA 재실행 편차(구분 한계 ≈ 2.2~2.3%p), 답변 프롬프트 효과(0.11~0.135).

## 6. 수치에서 이미 보이는 문제 후보

아래는 가설이지 결론이 아님. "확인할 것"은 기존 산출물을 읽는 작업이고,
"열리는 질문"은 카드의 연구 질문 후보임.

### T1. 벤치마크마다 다른 순위

같은 3 시스템의 순위가 벤치마크마다 다름. BEAM(100K·500K)은 LIGHT 1등,
Memora 전체 FAMA 는 v3(weekly 52.11) 또는 classic(monthly 35.15) 1등에
LIGHT 꼴찌, HaluMem QA 는 classic 과 v3 동률(차이 +1.01, 편차 범위 안).

- 확인할 것: 순위를 가르는 문항들의 유형. 과제 구성비를 바꿔 재가중하면
  순위가 어디까지 움직이는지 (기존 문항별 점수의 산수).
- 열리는 질문: 메모리 능력을 단일 점수나 순위로 요약하는 관행이 성립하는가.
  성립하지 않는다면 벤치마크는 점수 대신 무엇을 보고해야 하는가. 지금
  벤치마크들은 "어떤 기억 사용을 어떤 비율로 묻는지"를 스스로 명세하지 않는데,
  그 명세가 없는 리더보드가 무엇을 주장할 수 있는가.

### T2. 저장 지표가 좋아져도 QA 점수는 그대로임

HaluMem 20유저에서 저장물 지표는 v3 압승(F1 12.71 → 32.63)인데 QA 는 동률.
저장을 잘한다는 지표가 태스크 성능을 예측하지 못함.

- 확인할 것: v3 가 더 잘 저장한 골든들이 QA 문항에서 실제로 검색·사용됐는지.
  사용됐는데도 답이 같았는지, 아예 검색에 안 올라왔는지.
- 열리는 질문: 중간 지표(저장물 품질)가 최종 성능을 예측하지 못한다면
  메모리 벤치마크의 중간 지표는 무엇이어야 하는가. 태스크 성능을 예측하는
  저장물의 측정 가능한 속성이 존재하는가, 또는 저장물 평가라는 개념 자체가
  태스크와 분리될 수 없는 것인가. (다섯 난제의 관측 문제와 같은 뿌리)

### T3. 원문 반환 방식이 집계형 질문에 약함

LIGHT 는 remembering(weekly 72.41, 3 시스템 중 1등)과 BEAM 에서 강한데
reasoning 은 weekly 22.67, monthly 3.00 으로 크게 떨어짐. v3 는 반대로
reasoning 이 강함(weekly 52.67). 원문 pair 를 그대로 돌려주는 설계는 흩어진
항목의 집계·합성이 필요한 질문에 약하다는 가설.

- 확인할 것: reasoning 오답에서 필요한 근거가 컨텍스트에 있었는지. 있었다면
  실패 지점은 검색 이후의 독해·합성임. monthly 3.00 은 표본이 50문항이라
  판정 자체의 이상 여부도 봄.
- 열리는 질문: 질문 시점의 검색과 합성만으로 집계형 질문을 감당할 수 있는가,
  또는 저장 시점에 미리 계산해 둬야 하는가. 미리 계산하려면 무엇을 계산할지
  저장 시점에는 알 수 없다는 문제(내생성 난제)가 다시 나옴. 기억의 보관
  형태(원문·추출물·요약)와 질문 유형 사이의 적합성을 다루는 이론이 없음.

### T4. 정확도 표에 비용이 없음

정확도 표에 안 보이는 자릿수 차이가 있음. 투입 단위(mem0 세션 vs LIGHT
pair)가 HaluMem 기준 21.7배, v3 투입 토큰이 classic 의 2.34배, LIGHT 질의는
문항당 C+1콜(BEAM 100K 실측 C=172, 통과 12%). 임베딩 호출당 토큰은
classic 14.1 vs v3 392.4.

- 확인할 것: 정확도 1점당 비용을 세팅별로 계산했을 때의 재배열. 배포
  관점(채점 제외)에서 어떤 시스템이 모든 면에서 뒤지는지 (기존 계측 파일의
  산수).
- 열리는 질문: 비용을 통제하지 않은 정확도 비교가 벤치마크 결론으로 성립
  하는가. 같은 토큰 예산에서 비교하는 규약이 표준이 되어야 하는가. 시스템마다
  다른 투입 단위는 설계 철학이라 존중해야 하는 변인인가, 통제해야 하는
  교란인가.

### T5. 수치가 실험 절차에 민감함

답변 프롬프트 하나로 시스템 간 부호가 뒤집혔던 실측(−10.19 → +1.93),
judge 성향에 따른 절대 수치 이동, QA 재실행 편차 2%p대, 대화 단위 저장
개수 편차 11.1%.

- 확인할 것: 우리 세 벤치마크의 시스템 간 차이 중 몇 개가 편차 범위 안인지
  정리. 논문들이 주장하는 개선 폭과 이 편차의 크기 비교.
- 열리는 질문: 메모리 벤치마크 결과의 재현 규약이 없음. 무엇을 고정하고
  무엇을 함께 보고해야 결과가 재현 가능한 주장이 되는가. 절차 민감도가
  개선 폭과 같은 자릿수라면, 이 분야의 리더보드 축적은 무엇을 축적하고
  있는 것인가.

### T6. 갱신 능력 지표가 갱신 능력을 가려내지 못할 가능성

v3 는 ADD-only(갱신 없음), LIGHT 는 갱신 개념 자체가 없는 설계인데도
QA·FAMA 에서 갱신형 시스템(classic)에 밀리지 않는 세팅이 많음. HaluMem
update 채점과 Memora 망각 페널티가 갱신 능력을 분리해서 재는지 의심.

- 확인할 것: 갱신 실패가 최종 답변 오류로 이어진 사례가 실제로 몇 건인지.
  BEAM `100K_8|knowledge_update|0` (classic 만 갱신된 일정을 답하고 v3·LIGHT 는
  옛 일정을 답함) 같은 사례의 발생률. interference(미끼) FMR 도 같은 방식으로.
- 열리는 질문: 갱신·삭제 능력이 실제로 필요한 순간을 벤치마크가 충분히
  만들고 있는가. 무갱신 시스템이 벌점 없이 통과한다면 그 지표는 무엇을 재고
  있는가. 기억의 철회를 재는 평가는 어떻게 설계해야 하는가 (다섯 난제 중
  철회·지위 문제의 실증판).

### T7. 질문 시점 제약이 지켜지는지 검증할 수단이 없음

HaluMem 중간 시점 질의(47/65 세션)는 "그 시점까지의 기억"으로 답하기를
요구함. 최근성에 기대는 설계(LIGHT working memory)나 전량 저장 설계가 이
제약을 실제로 지키는지, 위반하면 벤치마크가 잡아내는지 확인 필요.

- 확인할 것: 시점 이후 정보가 있어야만 맞는 문항에서 각 시스템의 정오 분포
  (LIGHT HaluMem 완주 후).
- 열리는 질문: "그 시점의 기억"이라는 제약을 평가가 검증할 수 있는가.
  시점 위반이 점수에 잡히지 않는 평가 구조에서 시간 축 성능 주장은 무엇을
  의미하는가.

## 7. 진행 순서

1. **문항별 점수표**: `src/analysis/question_diff.py matrix` 로 벤치마크·세팅별
   문항 단위 시스템 점수표를 뽑음. 시스템 간 격차 큰 문항 순 정렬.
2. **사례 확인**: 격차 상위 + 문제 후보별 표적 문항을 `question_diff.py show` 로
   나란히 펼침(질문·기준·각 시스템의 답변·판정). 필요하면 trace 로 내려가
   검색 점수·추출 원문까지 봄.
3. **패턴 이름 붙이기**: 확인한 사례를 실패 유형으로 분류함. 유형이 5건 이상
   모이면 점수표로 돌아가 그 유형의 발생률을 셈 (일화에서 비율로).
4. **카드 작성**: §3 형식. 반례 검토 필드를 비우면 미완성임.
5. **종합**: 카드 간 관계(같은 뿌리인지, 독립인지)를 정리하고 연구 질문
   목록을 문헌조사 RQ 7건과 대조해 신규성 위치를 명시함.

## 8. 해석할 때 지킬 것 (CLAUDE.md 원칙의 재확인)

- 시스템 간 차이를 말하기 전에 재실행 편차(≈2.2%p)와 대조함. 범위 안이면
  "동률"로 씀.
- 교집합 유저·대화로만 집계함.
- 절대 수치는 judge 선택의 함수임. 카드의 수치 근거는 전부 같은 조건 안의
  상대 비교로만 세움.
- 수치는 산출물에서 재확인한 것만 인용함. 이 문서 §6의 수치도 분석 시작
  시점에 도구로 재확인하고 들어감.

## 9. 일정과 선행 조건

- 선행: lightmh 완주(HaluMem 20유저 투입 → 답변 → 채점), 대시보드 등록 확인,
  C 실측 갱신(`docs/light/light-review.md` §11).
- 분석은 산출물 읽기 전용이라 GPU 불필요. 서버에서 문항 대조, 로컬에서 카드
  작성.
- 순서: T1·T3·T4 (산출물 완비, 즉시 가능) → T2·T6 (HaluMem 레코드 조인 필요)
  → T5 (기존 실측 정리 위주) → T7 (LIGHT HaluMem 완주 후).
