# 종합 분석 계획: 수치에서 문제 정의로

작성 2026-08-29. LIGHT 전 벤치마크 완주 후 실행할 분석의 설계도임.

## 1. 목적

지금까지 쌓인 것은 "벤치 X의 지표 Y에서 시스템 Z가 몇 점"이라는 표면 수치임.
이 분석의 산출물은 점수표가 아니라 **현존 메모리 벤치마크와 메모리 시스템의
한계·맹점에 대한 problem statement 와 research question**임.

원칙 두 가지.

- **수치와 샘플을 항상 짝으로 읽음.** 집계 수치에서 긴장점을 찾고, 그 긴장점을
  만든 실제 문항·검색 결과·답변·판정을 눈으로 확인한 뒤에만 문제로 승격함.
  샘플 없는 문제 정의는 금지.
- **여러 개가 나와도 됨.** 하나의 큰 결론을 조립하려고 무리하지 않음. 카드
  단위로 독립적으로 성립하는 문제를 여러 장 만들고, 마지막에 관계를 정리함.

## 2. 산출물 형식: 문제 카드

카드 한 장 = 문제 하나. 필수 필드:

| 필드 | 내용 |
|---|---|
| 현상 | 무엇이 이상한가 (한 문장) |
| 수치 근거 | 우리 산출물에서 재확인한 수치 (경로 포함) |
| 샘플 근거 | 드릴로 뽑은 실제 사례 2~5건 (문항 키 포함, 재현 가능) |
| 반례 검토 | 이 현상을 평범하게 설명하는 가설들과 그 기각 근거 |
| 문헌 연결 | 문헌조사 RQ 7건 · 저장소 가설 리포트의 다섯 난제와의 관계 |
| Problem statement | 벤치마크의 맹점인지, 시스템의 한계인지, 둘 다인지 명시 |
| RQ | 검증 가능한 질문 형태. 가능하면 우리 산출물로 1차 검증 경로까지 |

최종 문서는 `docs/synthesis/problem-cards.md` (카드 모음) +
`docs/synthesis/synthesis.md` (카드 간 관계와 종합)로 나눔.

## 3. 증거 목록 (분석이 딛고 설 산출물)

3 시스템(mem0 classic 0.1.118 · mem0 v3 2.0.18 · LIGHT) × 3 벤치마크. 전부
동일 레인(agent gpt-oss-120b medium · 답변/채점 gpt-oss-120b high ·
Qwen3-Embedding-4B)임.

| 벤치마크 | 세팅 | 문항 단위 판정 | 경로 기준 |
|---|---|---|---|
| HaluMem | 20유저 (QA 3,467 · 평가 기준 18,415) | QA result_type + memory 4종 레코드 | `runs.yaml` halumem.scales.20u.by_system |
| BEAM | 100K·500K, BEAM 공식 프롬프트 레인 | 문항×cutoff 4벌 score(0~1) + nugget | beam.buckets.{100k,500k}-beamprompt |
| Memora | weekly·monthly | 문항 FAMA/MPA + criteria 단위 판정 | memora.periods.{weekly,monthly} |

수치 밖 증거:

- **trace**: 전 시스템·전 투입의 LLM(입력·출력 토큰)·임베딩·검색 호출 원문.
  검색이 무엇을 올렸는지, 추출이 무엇을 버렸는지 문항 단위로 복원 가능.
- **비용 계측**: `cost/{bench}-{setting}-{system}/` 스테이지별(투입·질의·답변·채점)
  호출 수·입력·출력·컨텍스트 분포.
- **재현성 실측**: 투입 반복 편차(전체 ±0.17%, 대화 단위 최대 11.1%),
  QA 재실행 노이즈(구분 한계 ≈ 2.2~2.3%p), 답변 프롬프트 효과(0.11~0.135).

## 4. 수치에서 이미 보이는 긴장점 (드릴 대상 후보)

아래는 가설이지 결론이 아님. 각 항목은 "드릴 질문"에 답한 뒤에만 카드로 승격함.

### T1. 순위는 벤치마크가 정한다

같은 3 시스템이 벤치마크마다 순위가 다 다름. BEAM(100K·500K)은 LIGHT 1등,
Memora 전체 FAMA는 v3(weekly 52.11) 또는 classic(monthly 35.15) 1등에 LIGHT
꼴찌, HaluMem QA는 classic과 v3가 동률(차이 +1.01, 노이즈 안).

- 드릴 질문: 순위를 가르는 문항들은 어떤 유형인가. 벤치마크의 문항 구성비가
  바뀌면 순위가 뒤집히는가 (과제별 재가중으로 1차 검증 가능).
- 문제 후보: "메모리 시스템 리더보드"라는 개념 자체의 성립 조건.

### T2. 저장 품질 지표와 최종 태스크의 절연

HaluMem 20유저에서 저장물 지표는 v3 압승(F1 12.71 → 32.63)인데 QA는 동률.
저장을 잘한다는 지표가 태스크 성능을 예측하지 못함.

- 드릴 질문: v3가 더 잘 저장한 골든들이 QA 문항에서 실제로 검색·사용됐는가.
  사용됐는데도 답이 안 바뀌었는가, 아예 안 불려왔는가.
- 문헌 연결: 저장소 가설 리포트의 관측 난제와 직결.

### T3. 원문 반환 시스템의 집계 붕괴

LIGHT는 remembering(weekly 72.41, 3 시스템 중 1등)과 BEAM에서 강한데
reasoning은 weekly 22.67, monthly 3.00으로 붕괴. v3는 reasoning이 강함
(weekly 52.67). 원문 pair를 그대로 돌려주는 설계는 흩어진 항목의 집계·합성이
필요한 질문에서 무너진다는 가설.

- 드릴 질문: reasoning 오답 샘플에서 필요한 근거가 컨텍스트에 있었는가.
  있었다면 실패는 검색이 아니라 독해·합성 단계임. monthly 3.00은 표본
  50문항이므로 판정 자체의 이상 여부도 확인.
- 문제 후보: 검색은 합성을 대신하지 못함. top-k를 늘려도 예산이 흡수하는
  구조(BEAM에서 실측)와 같은 뿌리인지 확인.

### T4. 비용 없는 리더보드의 맹점

정확도 표에는 안 보이는 자릿수 차이. 투입 단위(mem0 세션 vs LIGHT pair)가
HaluMem 기준 21.7배, v3 투입 토큰이 classic의 2.34배, LIGHT 질의는 문항당
C+1콜(BEAM 100K 실측 C=172, 통과 12%). 임베딩 호출당 토큰은 classic 14.1
vs v3 392.4.

- 드릴 질문: 정확도 이득 1점당 비용을 세팅별로 계산하면 순위가 어떻게
  재배열되는가. 배포 관점(채점 제외)에서 지배당하는(dominated) 시스템이 있는가.
- 문제 후보: 벤치마크가 비용 축을 보고하지 않아 생기는 왜곡.

### T5. 수치의 취약성 (프로토콜 민감도)

답변 프롬프트 하나로 시스템 간 부호가 뒤집혔던 실측(−10.19 → +1.93),
judge 성향에 따른 절대 수치 이동, QA 재실행 노이즈 2%p대, 대화 단위 저장
개수 편차 11.1%.

- 드릴 질문: 논문들이 주장하는 개선 폭들이 이 노이즈 바닥·프로토콜 민감도보다
  큰가. 우리 세 벤치마크의 시스템 간 차이 중 몇 개가 노이즈 안인가.
- 문제 후보: 메모리 벤치마크의 재현 규약 부재.

### T6. 갱신·삭제를 잰다는 지표의 실효성

v3는 ADD-only(갱신 없음), LIGHT는 아예 무갱신 설계인데도 QA·FAMA에서
갱신형 시스템(classic)에 밀리지 않는 세팅이 많음. HaluMem update 채점과
Memora 망각 페널티가 실제로 갱신 능력을 분리해서 재는지 의심.

- 드릴 질문: HaluMem update C/H/O와 Memora 페널티(FAMA−MPA 간극)에서
  시스템 간 차이가 나는 문항을 드릴. 갱신 실패가 최종 답변 오류로 이어진
  사례가 실제로 몇 건인가. interference(미끼) FMR도 같은 방식으로.
- 문헌 연결: 다섯 난제 중 철회·지위 난제의 실증판.

### T7. 시점성(temporal validity)의 회피 가능성

HaluMem 중간 시점 질의(47/65 세션)는 "그 시점까지의 기억"을 요구하는데,
최근성에 기대는 설계(LIGHT working memory)나 전량 저장 설계가 시점 제약을
실제로 지키는지, 벤치마크가 위반을 잡아내는지 확인 필요.

- 드릴 질문: 시점 이후 정보가 있어야만 맞출 수 있는 문항에서 각 시스템의
  정오 분포. LIGHT HaluMem 완주 후에만 가능.

## 5. 실행 프로토콜

1. **불일치 매트릭스**: `src/analysis/drill.py matrix` 로 벤치마크·세팅별
   문항 단위 시스템 점수표를 뽑음. 시스템 간 격차 큰 문항 순 정렬.
2. **샘플 드릴**: 격차 상위 + 긴장점별 표적 문항을 `drill.py show` 로
   나란히 펼침(질문·기준·각 시스템의 컨텍스트/답변/판정). 필요하면 trace 로
   내려가 검색 스코어·추출 원문까지 봄.
3. **패턴 명명**: 드릴한 샘플을 실패 유형으로 분류함. 유형이 5건 이상
   모이면 매트릭스로 돌아가 그 유형의 발생률을 셈 (일화 → 비율).
4. **카드 작성**: §2 형식. 반례 검토 필드를 비우면 미완성임.
5. **종합**: 카드 간 관계(같은 뿌리인지, 독립인지)를 정리하고 RQ 목록을
   문헌조사 RQ 7건과 대조해 신규성 위치를 명시함.

## 6. 해석의 방어선 (CLAUDE.md 원칙의 재확인)

- 시스템 간 차이를 말하기 전에 노이즈 바닥(≈2.2%p)과 대조함. 밴드 안이면
  "동률"로 씀.
- 교집합 유저·대화로만 집계함.
- 절대 수치는 judge 트랙의 함수임. 카드의 수치 근거는 전부 동일 레인 상대
  비교로만 세움.
- 수치는 산출물에서 재확인한 것만 인용함. 이 문서의 §4 수치도 실행 시점에
  드릴 도구로 재확인하고 시작함.

## 7. 일정과 선행 조건

- 선행: lightmh 완주(HaluMem 20유저 투입 → 답변 → 채점), 대시보드 등록 확인,
  C 실측 갱신(`docs/light/light-review.md` §11).
- 분석 자체는 GPU 불필요(산출물 읽기 전용). 서버에서 drill, 로컬에서 카드 작성.
- 순서: T1·T3·T4 (산출물 완비, 즉시 가능) → T2·T6 (HaluMem 레코드 조인 필요)
  → T5 (기존 실측 정리 위주) → T7 (LIGHT HaluMem 완주 후).
