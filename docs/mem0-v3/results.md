# mem0 v3 대 classic: 결과

계획·검증은 `implementation-plan.md`. 여기는 수치와 판독임.

**mem0 classic** = OSS 0.1.118 (2콜, ADD/UPDATE/DELETE, 임베딩 검색)
**mem0 v3** = 2.0.18 (1콜 ADD-only, 임베딩+BM25+엔티티 융합 검색)

둘 다 공식 구현임. 하네스·답변·채점·레인(gpt-oss-120b high) 전부 동일하고 `MEM0_IMPL` 로만 가름.

> 예전 문서에서 이 둘을 '팔 A / 팔 B' 로 불렀음. 프로젝트 안에서만 통하는 이름이라
> **메모리 시스템 이름을 그대로 쓰는 것으로 바꿈** (대시보드 표기와 일치).

> 판독 기준: 재실행 노이즈는 과제 단위 FAMA ±3~5, 전체 ±2~3 임 (`memora-experiment.md` §7-7).

### 1-1. reasoning +29.33 의 정체: 집계 문항에서 빠짐없이 긁어옴

reasoning 50문항의 승패를 가르면 **v3 가 한 문항도 잃지 않음.**

| | 문항 |
|---|---|
| 둘 다 맞음 | 21 |
| **A 틀림 → B 맞음** | **11** |
| 둘 다 틀림 | 18 |
| A 맞음 → B 틀림 | **0** |

Memora 의 `reasoning` 은 주간 집계 문항임. 한 사례를 끝까지 따라가면 이럼
(`startup_founder` / `activity_food_coffee_155`, 정답 **$70.46**).

| | 검색해온 커피 금액 | 합계 | 채점 |
|---|---|---|---|
| classic | 9건 `[6.64, 3.71, 5.42, 9.82, 6.83, 8.67, 6.65, 5.62, 3.30]` | **$56.66** | 오답 |
| v3 | 11건 (위 9건 + `9.26`, `4.54`) | **$70.46** | 정답 |

**정답을 외운 것이 아님.** 어느 메모리에도 70.46 이 없음. 개별 기록을 답변 모델이 더한 것임.
A 도 그 두 건을 **저장은 하고 있었음**(커피 금액 이벤트 11건). top-50 검색에 못 들어왔을 뿐임.

**집계 문항은 한 건만 빠져도 오답임.** 부분 점수가 없음. 그래서 검색 재현율의 작은 차이가
점수에서 크게 벌어짐.

> 이것은 `memora-experiment.md` §7-6 에서 세워둔 "규모 효과의 상당 부분은 검색 **예산**으로
> 설명되지 않는다" 와 맞물림. 예산이 아니라 **검색 방식**이었음. v3 는 예산이 아니라
> 신호를 바꿔서(BM25 + 엔티티) 그 격차를 건드림.

### 1-2. remembering·recommending 하락의 정체: 안 지워서 현재 상태를 못 말함

v3 가 제일 크게 진 문항들임.

| 문항 | A MPA | B MPA | |
|---|---|---|---|
| `activity_calendar_151` | 100 | **0** | "What upcoming events do I have in my calendar?" |
| `activity_todos_157` | 100 | **0** | "What tasks remain on my todo list this week?" |
| `activity_todos_147` | 100 | 25 | "What tasks remain on my todo list this week?" |

전부 **"아직 남은 것"** 을 묻는 문항임. 완료된 할 일과 지난 일정이 저장소에 그대로 남아
검색에 딸려오고, 답변이 그것들을 나열함.

무효 항목을 언급한 문항이 **67/98 → 79/98** 로 늘었고 FAA 가 52.32 → 39.98 로 떨어짐.

### 1-3. 한 줄 요약

**같은 성질이 한쪽에서는 이기고 다른 쪽에서는 짐.**

| | v3 가 이기는 곳 | v3 가 지는 곳 |
|---|---|---|
| 문항 유형 | 집계 ("이번 주 총합") | 현재 상태 ("아직 남은 것") |
| 기제 | 흩어진 항목을 빠짐없이 검색 | 완료·취소된 항목을 안 지워 계속 딸려옴 |
| 근원 | ADD-only + 3신호 융합 검색 | ADD-only (삭제 없음) |

**"add-only 가 낫다/나쁘다" 로 말하지 않음** (`implementation-plan.md` §2-6). 설계 수준으로
말함: **쓰기에서 정리하는 설계는 현재 상태 질의에 강하고, 읽기에서 선별하는 설계는 이력
집계에 강함.** Memora 는 둘 다 물어보므로 전체 점수는 상쇄되어 노이즈 안에 들어옴.

## 3. BEAM 100K (2026-08-26, 2026-08-27 정정)

> ⚠ **처음 낸 수치는 틀렸다.** 답변 생성 프롬프트가 두 팔에서 서로 달랐다.
> `answer_beam.py` 의 `BEAM_ANSWER_PROMPT` 기본값이 `beam`(BEAM 공식)인데
> `scripts/mem0-v3/run_all.sh` 가 그 값을 안 줬다. classic 쪽 대표 레인은 `mem0` 하네스
> 프롬프트로 돌린 것이라, 둘을 견주면 **메모리 시스템 차이가 아니라 프롬프트 차이를 읽게 된다.**
> BEAM 공식 프롬프트는 "설명 없이 답만 출력" 지시가 있어 전체 점수를 0.11~0.135 낮춘다
> (`beam-experiment.md` §7). 아래는 **프롬프트를 맞춘** 값이다.

대화 20 · 능력 10종 × 문항 16 × 대화 20 = 1,600. judge `openai/gpt-oss-120b` high.
양쪽 모두 **BEAM 공식 답변 프롬프트**.

| 능력 | classic | v3 | 차 |
|---|---|---|---|
| **multi_session_reasoning** | 31.28 | **45.77** | **+14.50** |
| **information_extraction** | 58.09 | **68.28** | **+10.20** |
| temporal_reasoning | 23.75 | 28.44 | +4.69 |
| instruction_following | 54.37 | 57.97 | +3.59 |
| summarization | 35.49 | 38.78 | +3.29 |
| event_ordering | 32.40 | 35.64 | +3.24 |
| contradiction_resolution | 5.94 | 7.42 | +1.48 |
| preference_following | 74.58 | 73.80 | −0.78 |
| knowledge_update | 44.38 | 42.19 | −2.19 |
| **abstention** | 44.38 | **25.62** | **−18.75** |
| **전체** | **40.47** | **42.39** | **+1.93** |

**전체는 v3 가 +1.93 으로 근소하게 앞선다.** 처음 적었던 −10.19 는 프롬프트 차이였다.

### 3-1. 철회한 주장: "모순 해소 49.30 → 7.42"

처음에 이 실험에서 가장 큰 수치라고 적었다. **틀렸다.**
같은 classic 투입·같은 검색 결과 위에서 프롬프트만 BEAM 공식으로 바꾸면 49.30 이 **5.94** 로 떨어진다.
v3 의 7.42 는 그 기준에서 **+1.48 로 오히려 높다.**

무너뜨린 것은 ADD-only 가 아니라 답변 규약이었다. "설명 없이 답만 출력" 지시가 있으면
모순을 짚어 설명하는 답을 안 쓴다. rubric 은 그 설명을 요구한다.

> 판독 규율: **한 벌만 보고 큰 수치에 서사를 붙이지 않는다.** 같은 축의 대조군이 리포에
> 이미 있었는데(`100k-beamprompt`) 그것과 맞추지 않았다.

### 3-2. 프롬프트를 맞춘 뒤 남는 차이

- **multi_session_reasoning +14.50 · information_extraction +10.20** 이 v3 의 진짜 강점이다.
  흩어진 근거를 모으는 문항인데, Memora 의 reasoning 상승(§2)과 같은 방향이다.
- **abstention −18.75** 가 v3 의 진짜 약점이다. 근거가 없을 때 없다고 말하는 능력인데,
  ADD-only 가 지우지 않아 저장소에 남은 옛 항목이 "근거가 있다"고 착각하게 만드는 것으로 보인다.
  (검증 안 됨. §4-1 과 같은 성격의 미결 항목임)

## 4. HaluMem (2026-08-26) · ⚠ 4유저 비교

**레인 제약을 먼저 적음.** 백본이 `gpt-oss-120b` 인 classic HaluMem 런은
`oss120b4` 4유저짜리 하나뿐임 (20유저 런 `full-traced` 는 백본이 Qwen3-4B 라 비교 상대로 못 씀).
v3 는 20유저로 돌렸으므로 **공통 4유저로 잘라서** 비교함
(`src/mem0-v3/compare_halumem.py`). 20유저 v3 집계본은 §4-2 에 참고로만 둠.

| 지표 | classic | v3 | 차 |
|---|---|---|---|
| 메모리 온전성 (weighted recall) | 42.77 | **51.37** | **+8.60** |
| 추출 F1 | 13.05 | **29.03** | **+15.98** |
| Target 정확도 | 99.28 | 98.25 | −1.03 |
| Interference 미포함률 | 63.16 | 53.02 | **−10.14** |
| 가중 정확도 | 98.25 | 95.35 | −2.90 |
| update Correct | 7.23 | **21.18** | **+13.95** |
| update Hallucination | 3.19 | 4.54 | +1.34 |
| update Omission | 89.58 | 73.45 | **−16.13** |
| QA Correct | 61.28 | 59.57 | −1.70 |
| QA Hallucination | 22.13 | 23.97 | +1.84 |
| QA Omission | 16.60 | 16.45 | −0.14 |

판정 건수: 온전성 1,861 · update 595 · QA 705 는 양쪽 동일(데이터셋 고정).
정확도만 3,508 대 4,279 로 다름 (저장 메모리 수가 달라서임).

**HaluMem 에서는 v3 가 메모리 쪽 지표를 크게 이김.** 추출 F1 이 2.2배, update Correct 가
2.9배임. classic 의 실패 양상이 Omission 89.58 이었다는 점이 열쇠임. classic 은 update 를
**아예 안 썼고**(`full-traced` 에서 UPDATE 19,752건 중 97%가 무변경으로 판명된 것과 같은 증상),
v3 는 ADD-only 라 갱신 내용을 무조건 새 메모리로 씀. 그래서 "새 내용이 있는가" 를 묻는
지표가 오름.

대가는 Interference 미포함률 63.16 → 53.02 임. 미끼를 더 많이 저장함. 많이 쓰는 설계가
많이 맞히고 많이 오염시킨다는 같은 이야기임.

**QA Correct 는 −1.70 으로 사실상 동률임.** 메모리 지표가 크게 올랐는데 QA 가 안 따라옴.
저장·추출을 잘해도 최종 답변까지 오지 못한다는 뜻이고, `mem0-halumem-baseline.md` 의
검색 병목 서술과 같은 방향임.

### 4-1. ⚠ 확인 못 한 것: update Correct 가 정당한가

HaluMem 의 `Correct Update` 판정 기준에는 **"원본 메모리가 교체되거나 낡은 것으로 표시될 것"**
이 들어 있음. v3 는 구조적으로 원본을 안 지움. judge 가 보는 `memories_from_system` 은
투입 **후** top-10 스냅샷이라 낡은 원본이 보일 자리에 있는데, 그럼에도 Correct 가 126건 나옴.

렉시컬 매칭(토큰 Jaccard)으로 "Correct 판정 건에 원본이 아직 남아 있는가" 를 세려 했으나
**실패함.** 골든 원문 표현과 mem0 저장 텍스트의 최대 유사도 중앙값이 양쪽 팔 모두 0.18 이라
임계값을 어디에 둬도 신호가 안 나옴 (classic 까지 0% 가 나온 것이 그 증거임).
**임베딩 매처나 LLM 대조가 필요한 별도 분석임.** 결론이 나기 전까지 update Correct +13.95 를
"v3 가 갱신을 잘한다" 로 읽지 않음.

Interference 47.02 · update C 22.36 / H 3.84 / O 72.87 · QA C 64.06 / H 20.25 / O 15.69.

## 4-3. 투입 재현성: 대화 단위는 최대 11% 흔들린다 (2026-08-27 실측)

비용을 재려고 mem0 v3 의 BEAM 100K 투입을 **같은 코드·같은 데이터로 한 번 더** 돌렸다
(`beam-100k-v3-cost`). 덤으로 투입 단계의 재현성을 처음 쟀다.

| | 본실험 | 재실행 | 차이 |
|---|---|---|---|
| 저장 메모리 총합 | 16,004 | 16,032 | **+0.17%** |
| 투입 단위(청크) | 2,866 | 2,866 | 일치 |
| 대화별 상대차이 | | | **중앙 4.1% · 최대 11.1%** |

**총합은 거의 같은데 대화 하나하나는 최대 11% 흔들린다.** 청크 수는 데이터가 정하므로 같고,
흔드는 것은 LLM 이 청크마다 몇 개의 사실을 뽑느냐다.

> 판독 규율: **대화 단위 저장량으로 순위를 말하지 않는다.** 10% 안쪽 차이는 재실행으로 뒤집힌다.
> 집계(20대화 총합) 수준에서는 ±0.2% 라 비용 비교에 쓰기에 충분하다.

이것은 QA 쪽 판독 한계선(`backbone-experiment.md` §17)과 같은 성격의 바닥값이고,
**투입 쪽에서는 이번이 처음 잰 것이다.**

**세 벤치마크가 같은 축을 가리킴.** 흩어진 근거를 모으는 문항(reasoning,
multi_session_reasoning, 추출)에서 v3 가 이기고, 지금 무엇이 참인지 묻는 문항

전체 점수의 부호를 정함.

> ⚠ 2026-08-27 정정 전에는 이 자리에 "BEAM 에서 모순 해소가 무너졌다" 고 적혀 있었다.
> 그것은 프롬프트 차이였다 (§3-1). **부호가 뒤집힌 자리가 있으므로 옛 판독을 인용하지 않는다.**

## 5-1. 배포 비용 (2026-08-27 실측)

BEAM 100K, 같은 20대화. 투입은 계측기로 직접 쟀고 답변은 산출물에서 되살렸다.
**답변 프롬프트를 맞춘 레인끼리** 견준다 (§3 참조).

| 단계 | | mem0 classic | mem0 v3 | 배수 |
|---|---|---|---|---|
| 투입 | LLM 호출 | 5,380 | 2,866 | **0.53배** |
| | 임베딩 호출 | (미계측) | 8,979 | |
| | 입력 토큰 | 9.45M | 31.4M | **3.32배** |
| | 출력 토큰 | 4.47M | 5.72M | 1.28배 |
| 답변 | 입력 토큰 | 1.68M | 3.81M | **2.27배** |
| | 컨텍스트 p50 | 4,375 | 9,375 | 2.14배 |
| **합계** | **토큰** | **15.9M** | **37.1M** | **2.34배** |

**호출은 줄고 토큰은 늘어난다.** v3 는 ADD-only 라 청크당 LLM 이 1콜(classic 은 추출+결정 2콜)인데,
고정 시스템 프롬프트가 8.4k 라 입력 토큰이 3.3배다. 임베딩도 청크당 3.1회 돈다.

답변 쪽 2.27배는 **같은 top-k 에서도 v3 메모리 항목이 길기 때문**이다. 검색 예산을 맞춰도
모델이 실제로 읽는 양은 두 배가 넘는다.

> 정확도는 프롬프트를 맞춘 기준 +1.93 이다 (§3). **그 이득에 2.34배 비용이 붙는다.**
> 어느 쪽을 고를지는 이 두 수치를 함께 놓고 정할 일이다.

⚠ classic 쪽 투입은 trace 에서 되살린 것이라 **임베딩 호출이 안 잡혔다** (tracer 가 LLM 만 감쌈).
호출 수 비교에서 classic 이 유리하게 보이는 만큼을 감안한다.

## 7. 다음: LIGHT (BEAM 논문 구현체)

BEAM 논문에 나오는 메모리 시스템 **LIGHT** 를 구현체를 찾아 같은 레인에서 돌린다.
대시보드는 이미 세 시스템 이상을 받게 돼 있으므로 붙이는 절차는 이렇다.

1. `runs.yaml` 의 `systems:` 에 항목 하나 추가 (`light:` label/version/note)
2. 각 벤치마크 세팅의 `by_system:` 에 `light:` 로 산출물 경로 추가
   (`halumem.scales.*` / `beam.buckets.*` / `memora.periods.*`)
3. 투입 스크립트에 `MEM0_IMPL=light` 갈래 추가 (`eval/mem0-classic-oss/*.py` 의 env 스위치와 동일 방식)

**지켜야 할 것은 레인 통제다.** 답변·채점 스크립트와 모델(gpt-oss-120b high),
임베더(Qwen3-Embedding-4B)를 그대로 쓴다. 그래야 mem0 두 벌과 같은 표에 놓을 수 있다.

⚠ 시스템마다 돌린 유저·대화 수가 다르면 화면과 문서 모두 **교집합으로 잘라 집계한다**.
HaluMem 에서 이미 겪은 문제다 (§4).
