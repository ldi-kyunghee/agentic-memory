### 1-1. reasoning +29.33 의 정체: 집계 문항에서 빠짐없이 긁어옴

reasoning 50문항의 승패를 가르면 **v3 가 한 문항도 잃지 않음.**

| | 문항 |
|---|---|
| 둘 다 맞음 | 21 |
| **A 틀림 → B 맞음** | **11** |
| 둘 다 틀림 | 18 |
| A 맞음 → B 틀림 | **0** |

Memora 의 `reasoning` 은 주간 집계 문항임. 한 사례를 끝까지 따라가면 이럼
(`startup_founder` / `activity_food_coffee_155`, 정답 **$70.46**).

| | 검색해온 커피 금액 | 합계 | 채점 |
|---|---|---|---|
| A | 9건 `[6.64, 3.71, 5.42, 9.82, 6.83, 8.67, 6.65, 5.62, 3.30]` | **$56.66** | 오답 |
| B | 11건 (위 9건 + `9.26`, `4.54`) | **$70.46** | 정답 |

**정답을 외운 것이 아님.** 어느 메모리에도 70.46 이 없음. 개별 기록을 답변 모델이 더한 것임.
A 도 그 두 건을 **저장은 하고 있었음**(커피 금액 이벤트 11건). top-50 검색에 못 들어왔을 뿐임.

**집계 문항은 한 건만 빠져도 오답임.** 부분 점수가 없음. 그래서 검색 재현율의 작은 차이가
점수에서 크게 벌어짐.

> 이것은 `memora-experiment.md` §7-6 에서 세워둔 "규모 효과의 상당 부분은 검색 **예산**으로
> 설명되지 않는다" 와 맞물림. 예산이 아니라 **검색 방식**이었음. v3 는 예산이 아니라
> 신호를 바꿔서(BM25 + 엔티티) 그 격차를 건드림.

### 1-2. remembering·recommending 하락의 정체: 안 지워서 현재 상태를 못 말함

v3 가 제일 크게 진 문항들임.

| 문항 | A MPA | B MPA | |
|---|---|---|---|
| `activity_calendar_151` | 100 | **0** | "What upcoming events do I have in my calendar?" |
| `activity_todos_157` | 100 | **0** | "What tasks remain on my todo list this week?" |
| `activity_todos_147` | 100 | 25 | "What tasks remain on my todo list this week?" |

전부 **"아직 남은 것"** 을 묻는 문항임. 완료된 할 일과 지난 일정이 저장소에 그대로 남아
검색에 딸려오고, 답변이 그것들을 나열함.

무효 항목을 언급한 문항이 **67/98 → 79/98** 로 늘었고 FAA 가 52.32 → 39.98 로 떨어짐.

### 1-3. 한 줄 요약

**같은 성질이 한쪽에서는 이기고 다른 쪽에서는 짐.**

| | v3 가 이기는 곳 | v3 가 지는 곳 |
|---|---|---|
| 문항 유형 | 집계 ("이번 주 총합") | 현재 상태 ("아직 남은 것") |
| 기제 | 흩어진 항목을 빠짐없이 검색 | 완료·취소된 항목을 안 지워 계속 딸려옴 |
| 근원 | ADD-only + 3신호 융합 검색 | ADD-only (삭제 없음) |

**"add-only 가 낫다/나쁘다" 로 말하지 않음** (`implementation-plan.md` §2-6). 설계 수준으로
말함: **쓰기에서 정리하는 설계는 현재 상태 질의에 강하고, 읽기에서 선별하는 설계는 이력
집계에 강함.** Memora 는 둘 다 물어보므로 전체 점수는 상쇄되어 노이즈 안에 들어옴.

## 2. Memora 세 기간 (2026-08-26)

세 기간 모두 페르소나 10 · 같은 데이터 · 같은 레인임. 기간이 길수록 세션이 쌓임.

| 기간 | 세션 | 문항 | A FAMA | B FAMA | 차 |
|---|---|---|---|---|---|
| weekly | 1,551 | 150 | 48.74 | 52.11 | +3.37 |
| monthly | 6,150 | 150 | 35.15 | 30.04 | **−5.11** |
| quarterly | 19,913 | 300 | 24.03 | 23.81 | −0.22 |

과제별로 쪼개면 **부호가 세 기간 내내 같음.**

| 과제 | weekly A→B | monthly A→B | quarterly A→B |
|---|---|---|---|
| reasoning | 23.33 → **52.67** (+29.33) | 8.00 → **26.00** (+18.00) | 5.00 → **12.50** (+7.50) |
| remembering | 71.18 → 60.13 (−11.05) | 47.91 → 28.95 (−18.96) | 29.09 → 26.23 (−2.86) |
| recommending | 51.70 → 43.52 (−8.18) | 49.55 → 35.17 (−14.38) | 37.99 → 32.70 (−5.29) |

**reasoning 은 언제나 오르고 remembering·recommending 은 언제나 내림.** §1-3 의 설계 해석이
세 기간에서 반복됨. 다만 **v3 의 우위 폭은 규모가 커질수록 줄어듦** (+29.33 → +18.00 → +7.50).
quarterly 에서는 양쪽 다 무너져서 (A 5.00 / B 12.50) 격차 자체가 작아짐.

quarterly 에서 전체 점수가 붙는 이유는 상쇄임. v3 는 MPA 가 더 높은데(33.04 → 35.40)
페널티도 더 큼(9.01 → 11.59). **더 많이 맞히고 더 많이 딸려옴.**

## 4. HaluMem (2026-08-26) · ⚠ 4유저 비교

**레인 제약을 먼저 적음.** 백본이 `gpt-oss-120b` 인 classic HaluMem 런은
`oss120b4` 4유저짜리 하나뿐임 (20유저 런 `full-traced` 는 백본이 Qwen3-4B 라 팔 A 로 못 씀).
v3 는 20유저로 돌렸으므로 **공통 4유저로 잘라서** 비교함
(`src/mem0-v3/compare_halumem.py`). 20유저 v3 집계본은 §4-2 에 참고로만 둠.

판정 건수: 온전성 1,861 · update 595 · QA 705 는 양쪽 동일(데이터셋 고정).
정확도만 3,508 대 4,279 로 다름 (저장 메모리 수가 달라서임).

**HaluMem 에서는 v3 가 메모리 쪽 지표를 크게 이김.** 추출 F1 이 2.2배, update Correct 가
2.9배임. classic 의 실패 양상이 Omission 89.58 이었다는 점이 열쇠임. classic 은 update 를
**아예 안 썼고**(`full-traced` 에서 UPDATE 19,752건 중 97%가 무변경으로 판명된 것과 같은 증상),
v3 는 ADD-only 라 갱신 내용을 무조건 새 메모리로 씀. 그래서 "새 내용이 있는가" 를 묻는
지표가 오름.

대가는 Interference 미포함률 63.16 → 53.02 임. 미끼를 더 많이 저장함. 많이 쓰는 설계가
많이 맞히고 많이 오염시킨다는 같은 이야기임.

**QA Correct 는 −1.70 으로 사실상 동률임.** 메모리 지표가 크게 올랐는데 QA 가 안 따라옴.
저장·추출을 잘해도 최종 답변까지 오지 못한다는 뜻이고, `mem0-halumem-baseline.md` 의
검색 병목 서술과 같은 방향임.

### 4-1. ⚠ 확인 못 한 것: update Correct 가 정당한가

HaluMem 의 `Correct Update` 판정 기준에는 **"원본 메모리가 교체되거나 낡은 것으로 표시될 것"**
이 들어 있음. v3 는 구조적으로 원본을 안 지움. judge 가 보는 `memories_from_system` 은
투입 **후** top-10 스냅샷이라 낡은 원본이 보일 자리에 있는데, 그럼에도 Correct 가 126건 나옴.

렉시컬 매칭(토큰 Jaccard)으로 "Correct 판정 건에 원본이 아직 남아 있는가" 를 세려 했으나
**실패함.** 골든 원문 표현과 mem0 저장 텍스트의 최대 유사도 중앙값이 양쪽 팔 모두 0.18 이라
임계값을 어디에 둬도 신호가 안 나옴 (classic 까지 0% 가 나온 것이 그 증거임).
**임베딩 매처나 LLM 대조가 필요한 별도 분석임.** 결론이 나기 전까지 update Correct +13.95 를
"v3 가 갱신을 잘한다" 로 읽지 않음.

### 4-2. v3 20유저 집계 (참고)

비교 상대가 없으므로 절대값으로만 둠. 온전성 54.06 · 추출 F1 32.63 · Target 98.19 ·
Interference 47.02 · update C 22.36 / H 3.84 / O 72.87 · QA C 64.06 / H 20.25 / O 15.69.

## 6. 비용 (2026-08-24 실측, TP=2 서빙 통일)

v3 는 **투입이 2.6배 느림.** 갱신 결정 LLM 호출을 없앴는데도 그런 이유는 추출이 훨씬 잘게
쪼개서 저장물이 3~6배가 되기 때문임 (`implementation-plan.md` §2-7).

| | 단위 | classic | v3 | 비율 | 저장물 |
|---|---|---|---|---|---|
| Memora | 세션 | 4.61초 | 12.25초 | 2.66배 | 171 → 1,005 |
| BEAM | 청크 | 3.74초 | 9.67초 | 2.59배 | 213 → 689 |

> 두 벤치마크가 일치함. 처음에 HaluMem trace 의 "갱신 결정이 투입 LLM 시간의 90.1%" 를
> 다른 벤치마크에 곱해 "10배 빨라짐" 이라고 추정했는데 정반대였음. 한 벤치마크의 비율을
> 다른 벤치마크에 외삽하면 안 됨.

### 서빙

| | 포트 | GPU | TP | util | max-model-len |
|---|---|---|---|---|---|
| 임베더 | 8001 | 2,3 | 2 | 0.18 | **32768** |
| LLM | 8002 | 2,3 | 2 | 0.75 | 32768 |

LLM KV 32.5 GiB · `Maximum concurrency` 46.07 · 무릎 c=12 (0.63 req/s · 1,063 tok/s).
TP=1 대비 **1.65배** (같은 벤치로 직접 비교).

⚠ 임베더를 4096 에서 32768 로 올려야 함. v3 는 `add()` 마다 **입력 대화 블록 전체**를
임베딩함 (기존 메모리 10건 조회용). BEAM 1M 청크 최대 20,351 토큰이라 4096 이면 대화가
통째로 실패함.
